## 1. 背景与问题

招聘负责人通常从零散的会议笔记、聊天记录或口头描述开始创建职位。信息往往不完整，且不同招聘人员对 JD 的结构、用词和发布标准不一致。现有表单适合编辑已知信息，却不能有效帮助用户完成“把模糊需求变成可审批 JD”的过程。

JD Copilot 是嵌入 JD Management 的任务型 Agent：将自然语言需求转换为结构化职位草稿，明确指出缺失与风险信息，并把所有对系统数据有影响的操作交还给用户确认。

## 2. 产品目标

1. 将一次非结构化职位描述转成可编辑的结构化 JD 草稿。
2. 在创建前识别并追问关键缺失信息，降低来回沟通成本。
3. 基于模板、职位规范和政策规则进行质量检查，帮助用户在提交审批前修正问题。
4. 保留人类对草稿、审批和发布的最终控制权。

### 成功指标（MVP 上线后观察）

| 指标 | 目标 |
| --- | --- |
| 从首次输入到保存首个草稿的中位时长 | 较手工创建降低 40% |
| 草稿创建过程中的必填字段完整率 | ≥ 90% |
| Agent 生成草稿被用户保留或部分应用的比例 | ≥ 70% |
| Agent 自动生成后仍因基础字段缺失被退回的比例 | ≤ 10% |
| 未经人工确认而触发审批/发布的次数 | 0 |

## 3. 用户与使用场景

| 用户 | 主要诉求 | 典型权限 |
| --- | --- | --- |
| Recruiter / TA | 快速把招聘需求转成合格 JD 并发起协作 | 创建和编辑草稿、提交审批 |
| Hiring Manager | 补充岗位职责、能力标准与团队上下文 | 编辑被授权字段、确认内容 |
| HR Approver | 确认内容、预算和合规风险已处理 | 审批或退回 |
| Viewer | 阅读 JD 与 Agent 结论 | 只读 |

### 核心场景

创建职位提供 **5 种并列方式**，对应不同用户的使用习惯（入口与流程详见 5.1）：

1. **回答 3 个问题快速创建（Quick Start）**：用户不确定 JD 该怎么写，直接用文字或语音回答 3 个问题——遇到的困难、希望候选人解决的问题、必备硬技能。Agent 据此推断职位名称并生成一份草稿；回答不全时只追问缺失的问题。在 Create a Job 首页直接输入自己的话（如“需要一位在胡志明市从零搭建增长体系的 Growth Lead”）时，同样进入这 3 个问题。
2. **从职位名称开始（Start with a Job Title）**：用户只输入职位名称，Agent 立即生成 3 份不同风格（简洁直接 / 亲切、以人为本 / 详细结构化）的 JD，用户对比后选择一份创建。
3. **上传已有 JD（Upload a JD）**：用户上传 PDF / DOCX / TXT 格式的 JD 草稿，Agent 抽取职位名称、职责、要求、加分项，以及文件中提到的地点和工作方式，直接生成结构化草稿，不需要额外配置步骤。
4. **粘贴链接或文案（Paste a Link or Text）**：用户粘贴外部职位链接，或复制来的 JD 正文 / 会议笔记，Agent 解析内容、标记来源，并改写为适合本公司的草稿。
5. **手动创建（Create Manually）**：用户希望自己掌控每个字段时，填写表单（必填：职位名称、地点、招聘人数、岗位职责、岗位要求；选填：级别、工作模式、部门、汇报线、含周期的薪资范围），保存后直接创建职位，不经过 AI 起草；缺失的内容由完整性检查提示。

创建之后：

6. **完善已有草稿**：用户在编辑页右侧 Copilot 面板（支持文字和语音）提出“把职责改得更偏 B2B 增长”，Agent 只生成可审阅的改动建议和 diff。
7. **提交前检查**：用户点击 **Analyze**，Agent 检查必填项完整性、待修改项（如无法验证的要求、级别与经验冲突）以及用词风险，并给出优化建议，结果显示在 **Analysis** 标签；存在缺失项或待修改项时 **Publish** 不可点击，也可一键由 AI 补全或修改。

## 4. 范围

### MVP 包含

- 通过 JD Copilot 提供 **5 种并列的创建职位方式**（Quick Start、Start with a Job Title、Upload a JD、Paste a Link or Text、Create Manually，见 5.1），接收文字、模拟语音输入、上传文件、链接和粘贴内容。
- 从输入中提取结构化职位字段：职位名称、部门/团队、地点、雇佣方式、职级、HC、职责、必备要求和加分项。
- 生成结构化 JD 草稿，并显示不确定项、缺失项和字段来源。
- 对缺失的关键字段进行追问。
- 生成对现有 JD 的新增、替换或润色建议；用户逐项确认后才写入。
- 进行基础完整性、逻辑一致性和文案风险检查。
- 保存草稿；在用户明确操作后提交审批。

### MVP 不包含

- 自动发布职位、自动撤回职位、自动发送外部消息。
- 直接修改预算、HC、审批人等受限字段。
- 代替审批人作出审批结论。
- 真实语音转写、外部 ATS/招聘渠道同步、薪酬市场定价。
- 在没有可追溯来源时，把推测信息写入正式 JD。

### 后续优先能力（P1）

- 职位市场薪酬调研与市场分位分析。
- 对标公司的公开 JD 检索、结构化对比与差异解释。
- 基于对标 JD 的结构参考，结合本公司画像生成定制化的新 JD。

## 5. 核心体验与入口

### 入口

- 职位列表页的 **Ask Copilot**：打开 **Create a Job** 首页（5 种并列的创建方式，见 5.1）。
- 已有 JD 的编辑页：右侧面板的 **Copilot** 标签（页面不再提供右下角浮动入口）。
- 选中文档内容后出现的 **Ask Copilot** 快捷操作。

### 展示方式

Copilot 始终从页面右侧打开为可拖拽宽度的侧边栏，不使用居中弹窗。

- **创建职位**：生成草稿后，右侧展开 **Workspace** 面板，与 **Ask Copilot** 面板左右并列，各有独立、等高的标题栏。Ask Copilot 面板标题栏提供 `新对话`；Workspace 面板标题栏提供 `收起 Workspace` 和关闭整个侧边栏的 `×`（Workspace 未展开时，`×` 在 Ask Copilot 面板标题栏）。
- **编辑已有 JD**：页面右侧面板有 **Copilot** 与 **Analysis** 两个标签，面板左边缘可拖动调宽（最窄 300px，最宽为窗口宽度的 60%，宽度在本机记住）。

### 侧边栏组成

1. 顶部：标题 `Ask Copilot`、`新对话`（清空当前对话并回到 Create a Job 首页，不关闭面板）、关闭按钮。
2. 会话区：用户消息为靠右的绿色气泡，Agent 回复为靠左的灰色气泡（不显示头像）；另有字段确认卡、缺失项和风险卡。
3. 任务操作区：`应用修改`、`保存草稿`、`提交审批` 等显式动作。
4. 底部输入卡片（固定在面板底部）：圆角卡片，上方为文本框；下方一排，左侧为麦克风、中间为状态文字（Listening… / Transcribing…）、右侧为圆形发送按钮（无内容时禁用）。回车发送，Shift+回车换行。选中文档内容时，选中文字的引用标签显示在输入卡片上方。

### 5.1 创建职位：5 种方式

首页标题为 **Create a Job**，副标题 **Choose how you’d like to start.** 5 种方式并列，彼此没有先后依赖，对应不同用户的使用习惯。每个入口只显示 **标题 + 一句话描述**，标题右侧有一个小 “i” 图标，点击后以提示条展示更多说明（是什么、适合什么情况、你要做什么）。

点击任一入口后，所选方式的标题先作为 **用户消息** 出现在对话中，随后由 Agent 以对话形式引导，不再出现额外的中间配置页。

| # | 入口标题 | 一句话描述 | 用户要做什么 | Agent 引导与处理 | 输出 |
| --- | --- | --- | --- | --- | --- |
| 1 | **Quick Start** | Answer 3 questions to create your JD. | 在一条消息里回答 3 个问题，可打字或语音 | 一次性发出 3 个问题：① 遇到了什么困难、为什么要招人；② 希望候选人解决什么问题；③ 候选人必须具备哪些硬技能。用户可一次回答（每行一个，编号可写可不写）；只答了一部分时，Agent 仅追问尚未回答的问题。根据回答推断职位名称；无法推断时追问“What job title should I use for this role?”，不留空 | 1 份 JD 草稿 |
| 2 | **Start with a Job Title** | Enter a title and get 3 JD options. | 在底部输入框输入职位名称 | Agent 只发引导文案，不弹输入框；用户输入后直接生成，不追问 | **3 份不同风格的 JD**（A Concise & direct、B Warm & people-first、C Detailed & structured），用户在对话卡片或 Workspace 页签中对比并选择一份 |
| 3 | **Upload a JD** | Upload an existing JD to refine and structure it. | 选择 PDF / DOCX / TXT 文件 | 点击入口即直接弹出文件选择；Agent 同时显示引导文案和 `Choose file` 按钮（取消后可再次打开）。选定文件后直接解析，不再有额外配置步骤 | 1 份 JD 草稿（尽量沿用文件中的标题、职责、要求、加分项，以及文件里提到的地点和工作方式） |
| 4 | **Paste a Link or Text** | Paste a job posting link or the full JD text. | 在底部输入框粘贴职位链接或完整的 JD 文案 | Agent 只发引导文案，不弹输入框。自动判断：以 `http://` 或 `https://` 开头的内容按链接解析；长度 ≥ 60 个字符或 ≥ 3 行的文字按 JD 正文解析；内容过短时提示重新粘贴，不报错 | 1 份 JD 草稿 |
| 5 | **Create Manually** | Fill in the details to build your own JD. | 填写表单并保存 | Agent 在对话中展示表单，不调用 AI 起草（见下） | 直接创建职位并进入编辑页 |

**Create Manually 表单**

| 类型 | 字段 |
| --- | --- |
| 必填 | Job title、Location、Headcount（正整数）、Responsibilities（每行一条，至少一条）、Requirements（每行一条，至少一条） |
| 选填 | Level（下拉：Intern、Junior、Mid、Senior、Staff、Lead、Manager、Director，默认不选）、Work model（Hybrid / On-site / Remote，默认不选）、Department、Reports to |
| 薪资范围（选填） | Minimum、Maximum、Currency（USD、VND、SGD、EUR、GBP、AUD）、Pay period（Hour、Day、Week、Month、Year） |
| 操作 | `Save`：校验必填项后直接按表单内容创建职位并跳转到编辑页；职责、要求按原样写入对应章节；薪资写入 Compensation 章节（如 “USD 25–40 per hour”）；不经过 Workspace 预览 |

校验失败时，对应字段标红并提示，不创建职位。

**各入口的共同规则**

- 方式 1、3、4 生成 **一份** 草稿；只有方式 2 生成三份。
- 草稿生成后，右侧展开 Workspace 预览；用户可 `Refine`（补充要求或修改地点/工作方式），Refine 同时作用于所有版本，并高亮改动处。
- 点击 `Create job from this draft`（三版本时为 `Create job with version A/B/C`）才会创建职位；创建者自动成为该职位的 Owner。
- 用户输入的内容在对话中只显示一次；输入框的提示语随方式变化（例如方式 2 为 “Job title, e.g. Growth Operations Manager”，方式 4 为 “Paste a link or the JD text…”）。
- 首页底部输入框保留：在首页直接输入文字，视为“用自己的话描述岗位”，Agent 会把它作为背景，继续发出 Quick Start 的 3 个问题。

### 5.2 创建后职位的默认值与展示

| 项 | 通过 Agent 创建（方式 1–4） | 通过 Create Manually |
| --- | --- | --- |
| Job title | 来自用户输入或推断；文档第一行大标题与页头职位名称为同一个值，改任一处都会同步 | 用户填写 |
| Location | 用户内容或文件里明确提到的地点；没有时默认 **Ho Chi Minh City, VN** | 用户填写 |
| Headcount | 默认 **1** | 用户填写 |
| Workplace type | 内容里明确提到的 remote / hybrid / on-site；没有时默认 **Hybrid** | 用户选择；不选则为空 |
| Level | 不设置（选填） | 用户选择；不选则为空 |
| Department | 能从岗位类型推断时填写（如 Finance），否则 **Unassigned** | 用户填写；不填为 **Unassigned** |
| 概述 | 生成一段正常的岗位介绍，不写“来源说明” | 不生成，由完整性检查提示补充 |
| Preferred | 默认可见范围 Public | 无 |

**编辑页字段行**：标题下方 **Location、Headcount、Workplace type 始终显示**；Level、Department、Team、Employment type、Hiring manager、Recruiter、Reports to、Priority 等其他选填项 **有数据才显示、没数据就隐藏**，可从 `Add field` 手动加入。系统自动填入的默认值（Employment type = Full-time、Priority = normal、创建时自动填成创建者的 Hiring manager / Recruiter）视为“没有数据”，用户修改过才显示。

## 6. 功能需求

### FR-1：需求理解与字段提取

Agent 接收自然语言或材料文本后，必须：

- 抽取可识别字段，并给出字段值、来源片段和置信度。
- 将“明确陈述”的内容与“Agent 推断/建议”的内容区分展示。
- 不将无法确定的信息伪装为已确认事实。
- 当输入包含多个岗位或相互冲突的要求时，先要求用户选择或澄清。

### FR-2：缺失信息追问

以下为创建可发布草稿的必填信息集（与《JD 完整性标准》一致）：职位名称、工作地点、招聘人数、职位概述、核心职责、任职要求，另含每块内容的可见范围、JD 唯一 ID 和语言版本（系统自动满足）。级别、部门、雇佣方式、工作方式、汇报线等为选填。

当关键字段缺失时，Agent 应：

- 创建职位的 Quick Start 方式一次性展示 3 个问题（困难、希望候选人解决的问题、必备硬技能），其余场景最多展示 3 个优先问题，避免表单式追问。
- 支持用户在一次回复中补全多个答案；只答了一部分时，仅追问未回答的部分。
- 允许用户选择“暂不确定”；该字段保留为未确认，提交审批时再按规则拦截或提醒。

### FR-3：JD 草稿生成

Agent 可生成以下结构：职位概述、职责、必备要求、加分项、地点与工作方式、团队/汇报信息（若已知）。

- 草稿必须遵循所选职位模板；未选择模板时使用系统默认模板并标识。
- 每次生成的草稿都应提供 `应用到草稿` 或逐项应用入口。
- 通过“输入职位名称”创建时，一次生成 3 份不同风格的草稿（Concise & direct / Warm & people-first / Detailed & structured），供用户对比选择；其他创建方式生成 1 份。
- Agent 不能直接覆盖用户已有内容；针对已有内容必须显示新增/替换 diff。

### FR-4：质量与风险检查

保存草稿和提交审批前，Agent 应至少检查：

| 检查类别 | 示例 |
| --- | --- |
| 完整性 | 是否缺职位地点、HC、职责或必备要求 |
| 一致性 | 职级与年限、地点与工作方式、HC 与审批状态是否冲突 |
| 文案质量 | 职责是否可执行、要求是否过于笼统、是否有重复表述 |
| 风险提示 | 是否出现歧视性、排他性或未确认薪酬/福利承诺 |
| 流程前置 | 是否存在未处理的必填项、未确认的关键字段或需要的审批人 |

检查结果分为：`阻断`、`需要确认`、`优化建议`。阻断项未解决时不可提交审批；优化建议不阻断保存。

### FR-5：写入与审批控制

| 动作 | Agent 是否可执行 | 要求 |
| --- | --- | --- |
| 生成建议 | 可以 | 不写入正式数据 |
| 应用某条文案或字段 | 仅在用户点击后 | 显示变更内容 |
| 保存草稿 | 仅在用户点击后 | 记录操作者、时间和来源 |
| 提交审批 | 仅在用户点击后 | 通过阻断检查后执行 |
| 发布、撤回、发送通知 | 不在 MVP 内 | 未来也必须显式确认 |

### FR-6：市场薪酬调研

用户可在创建或编辑职位时提出问题，例如“这个职位在上海的市场均价是多少？大厂和中小公司的区间分别是什么？”Agent 应生成一张可追溯的市场薪酬卡，而不是给出无依据的单一数字。

市场薪酬卡至少包含：

| 内容 | 要求 |
| --- | --- |
| 适用职位画像 | 职位、职级/年限、地点、工作方式、行业；缺失时先追问 |
| 统计口径 | 基本薪资、总包、月薪/年薪、税前/税后、币种及是否包含奖金/股权 |
| 分层区间 | 市场整体、对标大厂、成长型/中小公司；显示 P25、P50、P75 或等价区间 |
| 依据 | 数据源名称、采集时间、地域、样本量或可信度等级、计算/换算方法 |
| 结论与建议 | 与当前预算的差距、建议薪资带及需人工确认的假设 |

“大厂/中小公司”必须有可配置的业务定义，例如按员工人数、营收、融资阶段或企业分层库区分；不可只凭 Agent 主观判断。

当数据不足、来源冲突或样本量过低时，Agent 必须明确标记“证据不足”，展示可用来源及局限，不得伪造精确均价。所有薪资结论仅供招聘决策参考，不能被表述为法律、税务或保证性建议。

### FR-7：对标公司 JD 调研与对比

用户可指定一家公司或职位链接，要求查看“该公司的 JD 如何写、和我们当前 JD 有何不同”。Agent 应：

1. 检索或读取获授权的公开 JD 来源，并显示公司、职位、页面链接、地区、抓取/发布时间和可用性状态。
2. 把对标 JD 结构化为：职位定位、职责主题、必备要求、加分项、职级信号、工作方式、文化/雇主价值主张（EVP）和薪酬披露情况。
3. 与当前 JD 做维度化对比，明确展示“仅对标方具备”“仅我方具备”“共同具备”“表述方式不同但语义相近”的内容。
4. 输出可选改进建议，并说明建议来自对标模式、公司画像还是 Agent 自身推断。

对比结果必须引用来源片段或链接，且不得把受版权保护的完整 JD 大段复制到本系统。页面无法访问、内容已下线或来源不可靠时，应如实提示。

### FR-8：基于参考 JD 的个性化定制起草

用户可选择一份对标 JD 作为“结构参考”，再输入本公司的个性化信息，例如公司阶段/规模、所在行业、产品阶段、团队规模、文化、管理方式、工作地点、雇佣模式和该岗位要解决的业务问题。

Agent 应：

- 先提取参考 JD 的可复用结构、职责粒度和能力框架，而不是直接复制原文。
- 结合我方公司画像与职位需求，生成原创的职位概述、职责、必备要求、加分项和雇主价值主张。
- 对每项内容标注其来源类别：`参考结构`、`公司画像`、`用户明确要求` 或 `Agent 建议`。
- 在生成前追问会实质影响内容的缺失信息，如团队阶段、汇报对象、业务目标、地点和职级。
- 以 diff 形式交给用户审阅；用户确认前不写入 JD。

Agent 不得承诺薪资、福利、签证、远程政策、晋升机会或文化事实，除非该信息来自已确认的公司资料或用户明确输入。

## 7. 主流程

```text
用户描述需求
  → Agent 提取已知字段
  → 缺失/冲突？
      → 是：追问并更新结构化字段
      → 否：继续
  → 生成 JD 草稿与来源/置信度
  → 用户逐项应用或调整
  → Agent 运行质量检查
  → 用户保存草稿
  → 用户主动点击提交审批（满足阻断规则时）
```

## 8. Agent 行为边界

1. **可解释**：每个关键建议应能说明依据：用户输入、职位模板、历史 JD 或规则。
2. **最小行动**：默认只提出建议；任何写入、提交或外部动作均需用户显式触发。
3. **不确定性透明**：低置信度内容标为“待确认”，不得直接写入受限字段。
4. **权限感知**：当用户无编辑或审批权限时，提供可查看结论或“请求拥有权限的人处理”的动作，不展示不可执行的伪按钮。
5. **不制造事实**：不虚构预算、候选人供给、业务目标、法律结论或公司政策。
6. **可恢复**：应用修改后支持查看变更记录和撤销到上一版本。

## 9. 依赖与待确认项

| 依赖 | MVP 需求 |
| --- | --- |
| 职位模板库 | 每个模板的结构、必填字段、适用部门和版本号 |
| JD 数据模型 | 字段定义、编辑权限、审批状态和变更日志 |
| 政策规则库 | 禁用/风险用词、岗位合规提示、提交前置条件 |
| 用户与权限 | Recruiter、Hiring Manager、Approver、Viewer 的动作权限 |
| Agent 服务 | 文本理解、结构化输出、检索与工具调用的审计日志 |
| 市场薪酬数据 | 经过授权的薪酬调研数据、公开职位薪资数据或企业自有历史数据；需保留地区、日期和统计口径 |
| 对标 JD 数据源 | 合法可访问的公开职位页、已授权数据提供商或用户提供材料；需记录来源链接与抓取时间 |
| 公司画像库 | 公司规模、阶段、行业、产品、文化、工作方式、已确认的福利/雇主价值主张及版本 |

待产品与业务确认：最小必填字段清单、提交审批的阻断规则、默认 JD 模板、敏感字段定义、允许使用的历史 JD 范围、企业分层定义、可使用的薪酬与对标数据源、数据刷新频率及内容引用规则。

创建流程新增待确认项：① Agent 创建时的默认值（Ho Chi Minh City, VN、Headcount 1、Hybrid）是否需要在界面上标注为“默认”以便用户确认，以及是否与“不制造事实”原则冲突；② 上传文件支持的格式与解析方式（原型仅读取文本文件，PDF/DOCX 为模拟）；③ 粘贴文案的识别阈值（当前为 ≥ 60 字符或 ≥ 3 行）；④ 外部链接的抓取授权与版权边界；⑤ 职位名称的推断规则在无法判断时是否一律追问。

## 10. MVP 发布标准

MVP 可上线的前提：

- 用户可从 Create a Job 首页进入 5 种创建方式中的任一种，并完成一次到草稿（或到保存职位）的端到端流程；每个入口点击后直接进入对应的对话引导。
- Agent 会追问关键缺失字段，并区分明确事实和建议。
- 对已有 JD 的修改仅以 diff 建议呈现，未确认前不写入。
- 保存草稿、提交审批均由用户显式操作触发。
- 阻断检查会阻止不完整或存在关键冲突的审批提交。
- 每次 Agent 建议与用户应用操作均记录来源、时间和操作者。

# 基础流程核查

本清单用于读取当前项目权威规范后构建适用检查项。字段、枚举和具体门禁从实际模板与规范获取；本文件不替代它们。对每个 Issue/PR 输出规则来源、检查事实、pass/fail/unknown/na、证据链接及 na/unknown 原因。

## 仓库文件硬门槛

先按 [file-integrity.md](file-integrity.md) 递归核验流程根文件及本地引用闭包；确认任何必需文件缺失即直接不合格，先于样本和交付量判断。文件未知阻止合格及更高评级；不把仓库级缺失伪造成某个 Issue/PR 样本 fail。

## Issue

| ID | 检查内容 | 状态适用性 |
| --- | --- | --- |
| I-FORM | 所有共用和类型专属必填字段非空、标题唯一且独占三级行，名称与表单 label 一致；无提交占位符或 `_No response_`；字段内子标题四级或更深 | 所有样本；CLI/API 不因未使用表单而豁免 |
| I-CONTENT | Problem/Outcome/Scope/Non-goals 边界明确；Type、Risk、AI Ready、Estimate 等枚举有效；Owner 是实际监督者；依赖与引用可追踪；AI Ready=Yes 时必须是 Owner 已确认的具体点数，需求和依赖已澄清 | 所有样本；Yes/TBD 矛盾即使尚未实施也违规；允许 None/N/A 的字段须符合模板并解释原因，Owner 待分诊占位只有明确流程例外才可 na |
| I-AC | AC-1 等编号唯一且非空，输入、预期行为及可验证方式清楚，无影响实施的未决行为 | 所有样本检查 AC 格式；未决行为在未实施且 AI Ready=No 时可作为待澄清事项，不能据此认定违规实施 |
| I-READY | 首次实施前已 AI Ready=Yes、Owner 确认 Estimate，需有时间和来源；问题/依赖已澄清；估算依据留存 | 已进入实施的 Issue；单独 AI Ready=No/TBD 不违规，尚未实施时顺序项 na。当前正文变为 Yes 不证明开工前已就绪 |
| I-CHANGE | 决策和影响行为的变更已回写 GitHub，引用规格同步；未解决问题未被继续实施；开工点数保留，范围变化有原值、原因和决定 | 有相关事件时检查，不能因为没有六类前缀齐全就失败，也不能因旧 blocked 评论忽略后续解除 |
| I-CLOSE | 声称交付完成时逐项 AC 验收、相关验证与文档到位，有 Human Supervisor 依据，代码交付关联 PR 已合并 | 尚在进行为 na；取消/重复等有关闭理由即可，不要求未发生的交付验收，也不计周产出 |

类型专属检查依据对应 Form：Feature 用户流；Bug 复现、预期/实际、环境、严重程度（incident 是 Bug + 标签）；Design 用户流、平台、组件约束、异常状态和 handoff；Tech Debt 技术证据、兼容与回滚。若文档定义自动创建待分诊 Bug 等例外，引用精确条款，分别说明允许暂缺的字段及实施前补齐要求，不能扩展为所有机器人对象豁免。

## PR

| ID | 检查内容 | 状态适用性 |
| --- | --- | --- |
| P-FORM | PR 模板要求的二级字段标题完整、唯一，描述实际变更、规格引用、AC、证据、风险/回滚、文档、监督者 | 全部样本；草稿允许明确标记未完成的证据，无模板允许的例外仍应保留字段 |
| P-LINK | 正常实现关联恰好一个主 Issue，使用规范的 Closes 引用；依赖用 Refs；链接真实 Issue，读取全部讨论和引用需求 | 正常实现；例外须有当前项目正式规范依据。脚本允许 Fixes 等别名时依据实际契约说明，不凭字符串忽略关联语义 |
| P-AC | PR 与 Issue AC 逐项对应，提供已完成验证及证据，覆盖主流程和适用异常路径，范围与批准需求一致 | AC 映射所有阶段检查；尚未完成验收允许待办，已合并必须完成；N/A 须有具体依据 |
| P-EVIDENCE | 实际命令、退出码、日志/截图/报告对应正确 Issue、PR 和阶段提交（Review 为合并前最终 head，QA 为实际合并提交）；QA 逐项 AC，Review 独立检查 diff，安全审查有结论或适用性说明 | 已发生的验证与声称通过项；artifact 失效时可用同 SHA 长期台账及其他可复核来源，无法确认则 unknown |
| P-GATE | 合并前适用 Build/Lint/Type Check/Unit/Integration/Review 通过，顺序符合 CI；Human Supervisor 审批完成、阻塞发现和讨论解决；合并后 QA 验收实际合并提交，业务验收核对其证据；无绕过门禁 | 已合并 PR 核查合并前门禁；合并后 QA 仍 pending 时不把尚未完成的验收声称为完成。QA fail 需有分诊/修复依据，不能仅因发现缺陷就认定门禁被绕过；已确认绕过流程才 fail |
| P-DOC | 受影响 API/规格/设计/ADR/运行文档同步，或有 N/A 原因；风险与可操作回滚明确 | 按变更适用性；已合并时不得靠提交后补文档掩盖门槛缺失 |

按角色/变更检查补充证据：前端截图、浏览器/E2E、异常状态和设计差异；移动端平台、OS/设备矩阵及权限/恢复；后端 API 契约、迁移/兼容和必要 ADR；Agent/prompt 变更的 before/after eval、模型/配置、成本/延迟和失败分析。依据实际 Scope 判断适用性，不能要求纯文档 PR 必须有 UI 截图。

## 处理过程证据与边界

- 读取全部 Issue/PR 普通评论、PR reviews、行内评论、timeline、checks/workflow 和关联质量摘要，复核提交、审批、合并与关闭顺序。工作流文件存在不证明成功运行；PR 勾选通过不证明检查通过。
- 已合并 PR 分别核对最终 head 的合并前验证/审批和实际合并提交的 QA，不能用一个阶段或旧 SHA 的 pass 抵消另一个阶段或后来提交；授权例外必须引用正式决定及依据，不能由评估者发明例外。
- 若能够完整查询却确认必需记录不存在，记 fail（缺少规定证据）；读取失败、权限不足、被删除或过期而无法确认内容记 unknown。两者在报告中分列。
- 草稿不是所有要求的自动豁免：格式、链接和已发生行为仍检查；未来才要求的验收/审批项 na（尚未到该阶段），附原因。要声称基础通过，其他适用项均须 pass。
- 最新样本中的违规依据当前被评标准报告；最新 10 个只减少历史影响，不保证它们已采用新流程。不能额外跳过旧样本或擅自切换历史标准来提高评级；说明标准版本及迁移影响。
- 外部 Slack/聊天完整性无法从 GitHub 证明。检查可见决策是否回写，并披露观测范围；不要虚构对所有外部交流的审计。评估流程执行，不重新运行全部产品 QA，也不以抽样证明全部实现无缺陷。

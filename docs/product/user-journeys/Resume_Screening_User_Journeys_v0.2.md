# HireOS Command — Resume Screening 用户旅程与测试脚本

Doc ID: CMD-SCR-UJ-001  
Version: v0.2（测试对象为**已发布的线上地址**）  
Scope: Resume Screening 模块（岗位与筛选标准、导入简历、AI 推荐与关联、筛选评估与决定、候选人对比、任务）  
状态: 线上环境首次访问时为**空数据**（岗位列表与简历库都为空），侧栏目前只有 Jobs、Resume Library、Settings 三个入口；其余入口（任务、文件与集成、对比等）是否已上线需要实测确认，已在旅程清单里标出。  
用途: 用标准的用户旅程驱动测试。每条旅程既是“用户怎么用”的描述，也是可逐步执行、逐步打勾的测试脚本。

依据文档：`Resume Screening PRD v1.3`、`Resume Screening PRD v1.3 Patch 1`（置信度、no_match 判定线、评分维度配置、五档推荐阈值）、`HireOS Command JD Management PRD v1.3`（岗位要求的字段结构），以及第 9 节记录的已确认产品决定。**预期结果以这些文档和产品决定为准，而不是以线上当前表现为准**，这样线上与文档不一致的地方才会被测出来。

> 与 JD Management 旅程文档一样，这里测的是线上环境：数据不会因刷新而重置（是否持久化需要在 J10 里确认）、AI 输出每次可能不同。线上页面注明“所有数据均为虚构，外发、真实邮件与模型调用均为模拟”，所以**不会产生真实的外发后果**，但仍要遵守第 1.2 节的数据约束。Resume Screening 的核心是“AI 给建议、人来决定”，所以旅程里大量步骤在检查**AI 不自动拒绝、人工确认才生效、敏感信息不外露**这几条红线。

### 1.2 数据与安全约束（必须遵守）

1. **所有测试岗位、候选人名称加前缀 `[UJ-TEST]`**，例如岗位 `[UJ-TEST] Senior Backend Engineer II`、候选人 `[UJ-TEST] Nina Torres`，避免混入他人的数据，也方便清理。
2. **不使用真实候选人简历、真实邮箱、真实薪资和真实公司机密。** 所有简历用第 3 节自己编写的虚构内容；邮箱一律用 `example.com` 域名。
3. **线上首次进入是空数据，数据可能被他人共享或长期保留**（是否按浏览器隔离、是否持久化，在 J10 的 E12 里确认）。因此每条旅程所需的岗位和候选人都要**自己创建**，不依赖“恰好存在的示例数据”；创建前先在列表里搜 `[UJ-TEST]`，避免重复。
4. **不测试真实外发**：页面声明外发与模型调用是模拟的，但仍只用测试邮箱和测试候选人，不对任何真实地址发送内容；“拒绝通知”只对测试候选人发。
5. J5–J8 需要一组共用的岗位和候选人，已在第 3.4 节写成一次性的“标准数据集”，造一次后这四条旅程复用；若数据被删或被改，按 3.4 重造。J1–J4 和 J9–J10 各自新建自己的数据，互不依赖。
6. 测试完成后，把所有 `[UJ-TEST]` 岗位、候选人、连接归档或删除，并把清理结果写进测试记录；若线上没有删除入口，在测试记录里写明残留数据的名称。

### 1.3 执行与记录

1. 需要换角色时用 **Switch demo role** 切换，换完重新进入页面再检查。
2. 按旅程逐步执行，对每一步的“预期结果”标记 ✅ 通过 / ❌ 失败 / ⚠️ 部分通过。
3. 失败的步骤按第 6 节的模板记录缺陷，写明依据（文档章节）、环境与构建号。
4. 全部跑完后，用第 7 节的覆盖矩阵检查有没有漏测的需求。

## 2. 旅程的写法（模板）

每条旅程固定包含下面 7 块，写新旅程时照着填：

| 块 | 写什么 | 注意 |
| --- | --- | --- |
| 编号与名称 | J 编号 + 一句话目标 | 名称写用户目标，不写功能名 |
| 优先级 | P0 主流程 / P1 重要分支 / P2 边界与异常 | P0 必须每次发版后回归 |
| 角色 | 谁在做（对应一个演示角色） | 一条旅程只围绕一个主角色，换角色就写新的步骤段 |
| 前置条件与数据准备 | 角色、需要先制造出来的数据 | 线上不能依赖“示例数据”，要写清怎么造 |
| 测试数据 | 输入的文字、文件、名称 | 给出可直接使用的内容 |
| 步骤表 | `步骤 / 用户操作 / 预期结果 / 依据` | 一步只做一件事；预期结果写“看得见的现象” |
| 通过标准 | 整条旅程怎样算通过 | 例如“AI 推荐只出现在待确认列表，人工确认前不产生申请” |

写预期结果的原则：

- **可观察、可判定**：写文案、数字、状态（可点 / 不可点 / 显示 / 隐藏）。界面文案以当前语言的界面为准，文中括号里标注的是中文界面显示。
- **有出处**：每一步标注依据；没有出处的写“待确认”，并记为文档缺口。
- **AI 输出写“判定条件”，不写“固定文字”**：线上 AI 每次的措辞可能不同，所以写“理由是否引用了简历里真实存在的内容”“没有编造的经历或数字”，不写固定句子。同一输入至少跑 2 次，确认都满足判定条件。
- **加入产品红线检查**：AI 只给建议不自动淘汰；覆盖不足时不编造分数；敏感依据对无权限角色只显示结论；人工决定要留痕。
- **加入线上才有的检查**：刷新后数据仍在（持久化）、服务端校验（不能只靠前端拦截）、加载与失败状态。

## 5. 旅程详情

### J1 新建岗位，粘贴 JD 生成初始条件（P0）

**前置条件**：以 HR（Emma Wilson）登录，进入 Jobs（`/hireos/screening/jobs`）。首次进入列表为空；若已有测试数据，搜索 `[UJ-TEST]` 确认不重名。  
**测试数据**：新建岗位、粘贴的 JD（英文）。

| 步骤 | 用户操作 | 预期结果 | 依据 |
| --- | --- | --- | --- |
| 1 | 查看 Jobs 列表 | 默认进入列表；说明文字“每个岗位独立筛选…”；右上角主按钮 **New job**；表格列为岗位、状态、Resumes、Matched、Linked 等；底部有漏斗说明：统计的是**人数而不是文件数**，百分比为相对上一阶段的转化 | PRD 4.2；漏斗口径 |
| 2 | 点击 **New job** | 弹窗（标题 `Import / create job`）里有岗位名称、团队/职能（说明“用于从简历库做方向匹配”）、粘贴职位描述三项；有说明“仅凭职位描述即可创建项目，候选人可以稍后添加”；Jobs 列表本身没有单独的“上传简历”入口 | PRD 4.2 |
| 3 | 不填任何内容点 **Create draft job** | 提示岗位名称必填；不创建岗位 | 必填校验 |
| 4 | 只填岗位名称，点创建 | 提示团队/职能必填，并说明原因（用于从简历库做方向匹配）；不创建 | PRD 4.2 / Patch 1 P2 |
| 5 | 填岗位名称、团队，粘贴 JD（英文），点创建 | 创建成功提示；跳转到该岗位的标准页（Requirements & rubric）；岗位状态为草稿，尚未确认 | Patch 1 P3 |
| 6 | 查看标准页的结构 | 能看到 **AI 如何筛选**（默认收起、可展开）、**基础要求**、**业务要求**、**自定义条件**、**评分维度** 五个部分 | 已确认的产品决定 |
| 7 | 查看 **基础要求** | 由 JD 提取出**结构化字段**：工作年限 5 年以上、工作地点（越南、混合、河内）、学历（本科及以上）；每行是“字段名：值”，不是整句自由文本；**没有“工作授权”字段** | 已确认的产品决定：条件结构化，工作授权字段已移除 |
| 8 | 查看 **业务要求** | Go、Kubernetes、PostgreSQL 为 **Must-have**；Kafka、Redis 为 **Preferred**；页面上有说明“必须满足即硬性要求，不满足的候选人会被判为不符合资格；优先项是计分的加分项” | 已确认的产品决定；Patch 1 P3 |
| 9 | 查看 **评分维度** | 是系统给的通用中性起点，权重合计 100%；有提示说明这些维度尚未针对该岗位调整 | 已确认的产品决定：新岗位给中性起点 |
| 10 | 回到 Jobs 列表 | 新岗位出现，状态正常；Resumes / Matched / Linked 暂无候选人；**确认标准之前没有任何候选人被匹配** | 漏斗口径 |
| 11 | 刷新页面 | 岗位与标准仍在（持久化） | 线上专项 |

**通过标准**：岗位创建后落在标准页；JD 被转成结构化条件而不是一大段文字；默认评分维度有“未调整”提示；未确认前没有任何候选人被匹配。  
**常见失败点**：必填校验缺失；JD 里的 “Must have / Nice to have” 分错组；基础要求仍是自由文本；创建后直接就开始匹配（应在确认标准之后）；刷新后岗位丢失。

### J2 配置并确认岗位筛选标准，触发首次自动匹配（P0）

**前置条件**：HR 登录。**数据准备**：新建 `[UJ-TEST] J2` 岗位（团队 `Platform Engineering`，不粘贴 JD）；简历库里已有 3.4 的候选人（若未造，先造 3.4 第 ② 步，用于观察匹配结果）。  
**测试数据**：自定义条件（有效 / 应被拒绝 / 过于笼统）。

| 步骤 | 用户操作 | 预期结果 | 依据 |
| --- | --- | --- | --- |
| 1 | 在 **基础要求** 里点 **添加要求** 下拉 | 下拉里只列还没启用的字段：工作年限、工作地点、学历、语言、证书/资质、排除职称；**没有“工作授权”**；选一个后新增一行 | 已确认的产品决定 |
| 2 | 添加 **工作地点** | 有国家下拉、城市下拉（选了国家才列出该国城市）、现场/混合/远程选项；可加多个城市，以标签显示、可单个删除；**切换国家时已选城市被清空** | 已确认的产品决定：国家 + 城市 |
| 3 | 添加 **工作年限**，最少填 `5`，最多留空 | 摘要为“工作年限：5 年以上”；可切换“相关经验 / 总年限” | 已确认的产品决定 |

## 8. 与文档的已知差异（原型阶段的核对结果，线上需要重新确认）

| 项 | 文档要求 | 原型阶段的表现 / 已确认的产品决定 |
| --- | --- | --- |
| 推荐五档阈值 | Patch 1 P4：≥85 强烈推进、70–84 推进、50–69 待复核、30–49 暂缓、<30 不予推进，另有三条前置门槛（不符合资格、覆盖不足、未解决高严重度 Concern） | 原型的推断规则是：不符合资格 → 不予推进；证据不足 → 待复核；≥80 且合格 → 强烈推进；≥65 → 推进；其余待复核。**没有“暂缓”档，阈值与文档不同** |

## 1. 背景与目标

匹配和筛选的结论都以岗位标准为准。如果标准没有确认、硬性条件定义不清，或者标准改了之后旧结论被悄悄改写，AI 的建议就不可信。

**目标**：每个岗位有一份经人工确认、带版本的筛选标准；只有已确认的标准才能用于匹配和筛选；修改标准生成新版本，旧结果标为过期但保留。

## 3. 功能需求

| ID | 需求 |
|---|---|
| FR-1 | 岗位列表显示岗位、状态、Resumes、Matched、Linked 等列；漏斗统计的是人数而不是文件数 |
| FR-2 | **New job** 弹窗包含岗位名称（必填）、团队 / 职能（必填，用于从简历库做方向匹配）、粘贴职位描述；只有 JD、没有候选人也能创建 |
| FR-3 | 创建后进入标准页，状态为草稿；从 JD 提取出结构化条件 |
| FR-4 | **基础要求**为结构化字段：工作年限（最少 / 最多，相关经验或总年限）、工作地点（国家 + 城市，现场 / 混合 / 远程）、学历、语言、证书 / 资质、排除职称、薪酬范围（最小、最大、币种、周期、税前 / 税后，带「敏感」标签）；添加下拉只列出尚未启用的字段 |
| FR-5 | **业务要求**每条有优先级 Must-have / Preferred；页面说明 Must-have 即硬性要求，不满足判为不符合资格，Preferred 是计分的加分项 |
| FR-6 | **自定义条件**：输入后点「查看 AI 理解」，预览评估对象、判断规则、未满足和未知时的处理、可见范围后再添加；最多 10 条，带「内部」标签 |
| FR-7 | 自定义条件涉及受保护属性（性别、年龄等）时拒绝添加，并建议替代写法；过于笼统（如「Great person」）时要求改写成可在简历中验证的事实 |
| FR-8 | **评分维度**：新岗位给中性起点并提示「尚未针对该岗位调整」；维度 3～8 个，不重复，权重合计 100%；提供「平均分配」 |
| FR-9 | 权重不等于 100% 或维度数量不合格时，**Confirm criteria 不可点**（阻断，不是只提示） |
| FR-10 | 维度仍为默认值时确认，先弹出警示；确认版本后版本号 +1、页面只读 |
| FR-11 | 已确认版本不能就地修改；**Edit criteria** 生成下一版本草稿 |
| FR-12 | 新版本确认后，基于旧版本的推荐和评估标为「过期，可刷新」，不自动重跑、不改写 |
| FR-13 | 「AI 如何筛选」默认收起，展开后列出当前生效的条件数和判断方式，随标准修改同步 |
| FR-14 | 岗位列表区分「开放中」与「标准未确认」，标准未确认的岗位不能用于匹配 |

## 4. 业务规则

| ID | 规则 |
|---|---|
| BR-1 | 只有已确认（confirmed）的标准能用于岗位推荐和筛选；首次确认后才触发自动匹配 |
| BR-2 | 是否硬性由岗位确认版本决定；Must-have 即硬性；AI 不能自行把 Preferred 升级为硬性 |
| BR-3 | 筛选中不使用「工作授权」字段类型，只用工作地点（国家 + 城市）（产品决定，PRD §5.2 待同步） |
| BR-4 | 薪酬比较前先统一币种、周期、税前 / 税后；无法统一时为 unknown |
| BR-5 | 受保护属性及其明显代理不能成为筛选条件 |
| BR-6 | Screening 可独立使用，所有条件都可编辑，字段结构与 JD Management 的要求结构一致；修改不回写 JD |
| BR-7 | 从 JD Management 导入时只保存快照，不直接读写 JD 数据库 |
| BR-8 | 薪酬最小值不能大于最大值；服务端也要校验所有规则，不能只靠前端拦截 |

## 5. 数据

| 方向 | 对象 | 关键字段 |
|---|---|---|
| 输入 | JD 文本 / RoleCriteriaSnapshot | 岗位名、团队、要求原文、来源版本 |
| 输出 | Job | 名称、团队、状态、标准状态、负责人 |
| 输出 | JobCriteriaVersion | 版本号、状态（draft / confirmed）、基础要求、业务要求、自定义条件、维度与权重、确认人、确认时间 |

## 6. 权限

- 只有岗位标准负责人可以编辑和确认标准；HR Approver、Viewer 不可编辑。Patch 1 P3 中「Admin 可编辑任意岗位」在四类角色下暂无对应角色（见 [README 权限矩阵](../README.md#角色与权限)）。
- 薪酬范围和内部自定义条件只对内部可见，不出现在对外材料中。

## 7. 非功能要求

- 双击确认、创建只生效一次。
- 两个标签页同时编辑同一岗位标准时，有冲突提示，不静默覆盖。

## 8. 验收标准

| ID | 验收 | 对应 |
|---|---|---|
| AC-1 | 只有 JD 也能创建岗位；之后加入候选人可独立完成筛选 | SCR-01、J1 |
| AC-2 | JD 被转成结构化的基础要求，Must-have / Preferred 分组正确 | J1-7～8 |
| AC-3 | 受保护属性条件和笼统条件被拒绝 | J2-8～9、E6 |
| AC-4 | 权重不等于 100%、维度少于 3 或多于 8 时无法确认（服务端同样拒绝） | J2-13～15、E12 |
| AC-5 | 确认前没有候选人被匹配；首次确认后才触发匹配，结果只进入待确认 | J1-10、J2-17～18 |
| AC-6 | 修改已确认标准生成新版本；旧结果标过期但保留，可追溯到旧版本 | SCR-07、J7 |
| AC-7 | 标准未确认的岗位不显示为可匹配的开放岗位 | #12 |
| AC-8 | 非标准负责人（含 HR Approver、Viewer）不能编辑或确认标准，接口返回 403 | Patch 1 P3 |

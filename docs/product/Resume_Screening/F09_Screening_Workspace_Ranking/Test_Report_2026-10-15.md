## 5. UX/UI 审查

### 5.1 发现及修复验收

| ID | 级别 / 类别 | 角色与旅程步骤 | 证据、用户影响、最小修复方向 | 复测标准 |
|---|---|---|---|---|
| UX-F09-01 | **P1 / clarity、state** | Recruiter，步骤 2–3 | E-02：不符合条件的 92 分排在符合条件的 91 分前；粗体大分数先于资格结论被注意到，容易把“高分”误读为“先推进”。按 Eligibility 明确分组，并在组内按分数、覆盖率排序；资格、AI 与人工结论建立清晰优先级。 | 同一基线内按资格分组；最高分不符合条件者不会在符合条件组前被当作首选；文字说明不依赖颜色。 |
| UX-F09-02 | **P2 / efficiency、state** | Recruiter，步骤 5 | E-03/E-04：筛出“需要核实”后打开详情，返回即恢复全部三人且滚动到顶部，需重新查找。保存筛选条件和列表位置。 | 设定条件并进入详情，返回后条件、结果、滚动位置保持。 |
| UX-F09-03 | **P2 / accessibility** | Recruiter，步骤 15 | E-06：1024 宽度时表格末列溢出并出现横向滚动；主要“打开”动作藏在右侧。窄屏时收起非关键列或调整布局。 | 1024 宽度无需横向滚动即可见资格结论和打开入口。 |
| UX-F09-04 | **P1 / next_action、clarity** | Recruiter，步骤 1、7、10 | E-01/E-05/E-08：未显示排序基线、批量筛选或逐人勾选/批量决定；“候选人对比”直接使用全体三人，用户不能在工作台控制交接对象。先明确当前能力范围及不可用原因，再提供批量动作和可见反馈。 | 首屏可识别排序基线、可选对象及可用的批量动作；失败重试有逐条状态和操作结果。 |

P1 是基于当前主流程的注意力分配和下一步受阻；未验证的批量/权限能力不能据此推断线上 API 必然不存在。由于 UX-F09-01 和 UX-F09-04 未关闭，且 P0 用例失败/缺证据，整体不予放行。

## 6. 仓库静态核对与后续复测

当前仓库的 [`ScreeningWorkspacePage.tsx`](../../../../hireos-screening/hireos-screening-front/src/pages/ScreeningWorkspacePage.tsx) 中，`eligFilter` 只放在页面本地 state；列表排序以 `overall` 降序为主；对比把 `rows.map(...)` 全部传入创建接口；工作台行有鼠标 `onClick`，未设行级键盘焦点。后端 `RankingSnapshot` 的创建代码位于 [`comparisons.service.ts`](../../../../hireos-screening/hireos-screening-backend/src/comparisons/comparisons.service.ts)，属于对比快照流程。**以上仅为当前仓库静态观察，不能作为线上 API 或线上构建的证明**；线上表格列序与当前代码亦有差异。

复测顺序：

1. 先准备不含个人信息的隔离 seed：不同资格状态、同分、无总分、标准 v1/v2 与未映射量尺；取得线上构建号、API 响应及 RankingSnapshot 记录，复测 UC-01、03、04、08。
2. 在工作台补齐过滤、个人置顶、逐人勾选、批量运行/重试/取消后，用隔离 `llm_fail` 样本核对任务状态、成功项不重复分析、Application 数不变；复测 UC-05～09。
3. 用 Recruiter、HM、HR Approver、Viewer 和跨岗位无权限账号分别检查 UI 与 API，包括受限字段和 403；复测 UC-06、10～12。
4. 在 1024 宽度和 200% 缩放下执行键盘 Tab/Enter、焦点顺序与主要操作检查；复测 UC-13。对 UX-F09-01～04 逐项记录修复证据或正式豁免。

**最终判定：fail / 不通过完整验收。** 本报告已覆盖 13 条用例、7 项 AC、U1–U10 和线上证据边界；未执行项维持“未验证”。没有创建或关闭 Issue、push、部署或操作生产服务器。

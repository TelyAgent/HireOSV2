## 1. 背景与目标

一个岗位往往同时有几十上百个候选人。HR / HM 需要知道先看谁、哪些人需要先核实，并能成批运行评估，但排序只是分配注意力，不是结论。

**目标**：在一个岗位下集中审阅全部已关联候选人；只在同一评估基线内排序；支持批量运行和失败重试；把待确认推荐和已关联候选人分开。

## 3. 功能需求

| ID | 需求 |
|---|---|
| FR-1 | 顶部显示岗位、标准版本、候选人数、排序基线；左侧候选人列表，右侧详情 |
| FR-2 | 「AI Suggested candidates（待确认推荐）」和「Linked candidates（已关联候选人）」分区显示，人数分别统计 |
| FR-3 | 已关联列表显示 Eligibility、总分、覆盖率、AI 建议、人工状态；信息有主次层级，结论类信息突出 |
| FR-4 | 过滤：Eligibility（Eligible / Needs verification / Not eligible）、状态、维度、来源、负责人、覆盖率；返回时保留过滤条件和滚动位置 |
| FR-5 | 默认排序：在各 Eligibility 分组内按总分降序、覆盖率降序；同分同名次；没有总分的进入 Needs Verification 分组，不排在最后一名 |
| FR-6 | 个人可以置顶（pin）候选人，只影响自己的视图 |
| FR-7 | 勾选多名候选人后可以进入对比（F10）或批量决定（F11） |
| FR-8 | 批量运行筛选：显示 queued / running / completed / failed / cancelled 数量；失败条目可重试；取消只停止未完成的条目 |
| FR-9 | 评估过期的候选人显示「Refresh available」，可单个或批量刷新 |
| FR-10 | stale、pending、empty、error、partial、无权限状态各自有设计 |

## 4. 业务规则

| ID | 规则 |
|---|---|
| BR-1 | 只在同一 workspace / 岗位 / 标准 / 策略 / rubric / 模型和 prompt 基线 / 生效偏好 / 评分算法下排序；不同基线分组显示，旧结果不直接混排 |
| BR-2 | 新增候选人生成新的排序快照，不改历史快照 |
| BR-3 | 排序快照记录全部成员及结果版本、排序算法、生成时间和排除原因 |
| BR-4 | 个人偏好排序单独命名保存，不改变团队排序 |
| BR-5 | 来源只用于运营过滤，默认不参与加权 |
| BR-6 | 批量筛选锁定一个岗位评估基线，每个候选人是独立任务；运行中修改岗位版本不影响当前批次，新版本需要新批次 |
| BR-7 | 重试不重复分析成功项，不重复创建人或 Application |
| BR-8 | 机器运行任务和人工待办分开统计 |
| BR-9 | 「选择全部」不能悄悄包含之后新增的候选人 |
| BR-10 | 不用红绿颜色作为唯一的语义表达 |
| BR-11 | 过滤条件保存在页面地址中（#198）：浏览器返回、刷新页面和复制链接都保留同一组条件；未设置的条件不写入地址；“清除过滤”恢复全部。滚动位置只在浏览器返回时恢复，新打开或刷新页面从顶部开始。“维度”过滤的具体口径待确认（见 §10） |

## 5. 数据

| 方向 | 对象 | 关键字段 |

| 输入 | ScreeningEvaluation | 结果版本、基线信息 |

## 6. 权限

- 只显示当前用户对该岗位有权查看的候选人；团队统计按权限展示。

## 7. 非功能要求

- 键盘可以操作列表行（见 #25）。

## 11. 批次实施与验收边界

详见 [Batch Execution and Recovery](Batch_Execution.md)。工作台复用当前已关联候选人的选择集合，确认弹窗冻结成员；新增候选人不会自动加入。启动请求在发送前保存会话级幂等键，响应丢失后刷新仍沿用原请求。无法保存请求标识时不发起运行。

批次区独立显示机器任务的 queued/running/completed/failed/cancelled/unknown 数量，不加入人工待办计数。每 5 秒回读持久状态，读取失败明确提示旧数据可能过期。可取消排队项、只重试明确失败项；未知项只有核对入口，不自动重跑且保留执行名额。界面展示最近 50 个批次，不宣称这是全部历史。

前端使用真实后端批次 API；本地端到端测试只在临时 PostgreSQL schema 中运行，替换 AI 为可控边界，不发送真实候选人信息。局部测试不能代替生产部署验收，父 #200 在两段证据齐全前保持打开。

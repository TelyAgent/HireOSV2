## 4. 缺陷与复测标准

### F-01 · P1 · 百分比权重未经有效门禁进入已确认产物

- **角色/步骤：**HR/HM 审核并确认标准，J5 / UC-I03-03 / AC-2。
- **证据：**A 总计 610% 但 Confirm 可操作；B 的 confirmed v1 总计 105%，评估包继续显示同组权重。本地 `rubric.service.ts` 的 `confirm()` 只校验版本/草稿状态，未见合计 100% 检查；`contracts.ts` 只限制单项 0–100。代码仅为旁证，不证明线上部署版本完全一致。
- **影响：**加权评分与覆盖率口径失真，异常可成为后续人工决策的正式依据。当前证据不能证明线上计算公式或当前 610% 点击后的服务端响应。
- **修复/验收：**总计不是 100% 时显示明确差额、禁止确认，后端同样拒绝；用隔离项目分别测 95/100/105%，并核对已确认的 105% 历史数据如何修复或标注。

### F-02 · P0 · 已用于面试的 Rubric 无法按 I03 AC-4 建立新版本

- **角色/步骤：**HR 对已有评分的标准纠错或响应 JD 变化，J7 / UC-I03-07 / AC-4。
- **证据：**B 的评分表没有 New version 入口，明确显示“已用于计划，不能再版本化”。本地 `RubricPage.tsx` 对 `frozen` 状态隐藏该入口，`rubric.service.ts` 的 `newVersion()` 遇到已确认计划返回 `RUBRIC_LOCKED`。页面顶部仍称后续编辑会创建新版本。
- **影响：**I03 规定的“保留旧分绑定 v1，同时新建 v2 草稿”主路径无法完成；之后继续面试只能沿用旧标准或另起工作流。此定级针对当前 I03 草稿 AC；如果产品决定永久冻结，应先修改 AC、JD 更新规则和用户旅程。
- **修复/验收：**保持 v1 只读，允许显式复制为 v2 草稿；原评分继续引用 v1，新计划使用经确认的 v2，并在 UI 显示两版关系。以已评分 seed 核对 UI、API、DB 三处。

### F-03 · P1 · 能力验证卡缺少 I03 要求的判断信息

- **角色/步骤：**HR/HM 核查能力与证据，J2 / UC-I03-05 / PRD FR-3、FR-6。
- **证据：**A、B 的 Rubric 卡可见要求、优先级、权重和 Expected evidence；没有 Required L、简历对应 Claim、无匹配提示或 STAR 追问。打开 A 编辑面板也没有 Required L 字段。
- **影响：**确认者不知道岗位通过门槛，也不能在同一能力卡判断“简历声称了什么、还需怎么追问”，影响面试准备与标准复核。
- **修复/验收：**逐卡展示 Required L 与含义；有简历时显示来源明确且标为待核实的 Claim，无匹配时显示指定空状态；展示 STAR 追问及来源。用有/无简历两个隔离 seed 验证。

### F-04 · P2 · 逐卡 JD 原文与来源版本无法在页面定位

- **角色/步骤：**HR 对照 JD 审核 AI 草稿，J2 / FR-3 / BR-7。
- **证据：**卡片显示要求文本，但没有可见的 JD 原段落或版本入口；Overview 只写 JD Provided。本地 API 类型包含 `sourceRefs`，页面没有呈现该字段。
- **影响：**多个相近要求被拆分、合并或 JD 变更时难以追溯。此结论只针对可见页面，不能推断数据库没有来源记录。
- **修复/验收：**显示来源 JD 版本和原文片段定位；人工增补标注为建议。随机抽查卡片能打开对应版本，JD 更新后能识别待复核项。

### F-05 · 已撤回 · 未确认时页底继续按钮无反馈

2026-10-15 复测时，点击未确认 Rubric 页底 `Continue to interview plan` 后，页面顶部出现 `Confirm the rubric in Requirements & Rubric first.` toast，且没有进入计划。原测试只查看点击后的可访问性树，未检查短暂显示的视觉 toast，因此将“无反馈”误报为缺陷。此项不计入有效发现，不应创建 Issue；保留编号以便追溯原草稿。

### F-06 · P2 · 编辑一张能力卡会改变整组卡片顺序

- **角色/步骤：**HR 编辑草稿中的单项权重，J4 / PRD FR-7。
- **证据：**A 原第一张卡权重 100%，原最后一张卡权重 65%。把第一张的权重改成 99% 保存后，原第一张移到列表末尾、原最后一张移到首位；刷新后顺序仍变。再把 99% 恢复为 100%，数值已恢复，顺序没有恢复。最终截图保存在本机路径（见第 1 节）。
- **影响：**单字段修改意外重排能力列表，审核者可能误以为优先级或 JD 顺序被修改，也增加前后版本对照成本。本轮未观察到权重以外的字段值变化。
- **修复/验收：**保存时保留显式 `sortOrder` 或稳定排序键；只改某一张卡的权重后，全部卡片仍按原顺序显示；刷新和第二次编辑后保持一致。

### F-07 · P2 · Rubric 缺少导出入口

- **角色/步骤：**HR/HM 在确认前后导出岗位评分标准，J9 / PRD §2。
- **证据：**草稿 A 与已确认 B 的 Requirements & Rubric 页面均没有 Rubric 导出控件；本地 `RubricPage.tsx` 也未见导出操作。未验证是否存在未暴露的 API，亦未验证 I13 Activity。
- **影响：**无法从 I03 页面取得可共享、可追溯的标准版本；PRD 要求的导出及活动记录无法从主旅程完成。
- **修复/验收：**提供清楚标注版本的导出操作；产物包含能力、权重、等级锚点、来源和确认信息，I13 Activity 记录操作与结果。自动测试覆盖草稿/确认版及无权限用户。

### F-08 · P2 · 已确认 Rubric 页面未展示确认人和确认时间

- **角色/步骤：**HR/HM 追溯评分标准的人工确认，J10 / PRD FR-8。
- **证据：**B 仅显示 `Rubric v1 confirmed`，没有确认人或时间。API 类型含 `confirmedBy`、`confirmedAt`，但本轮未在线读取这两个字段；评估包中的 HR/HM 最终决定确认属于另一个对象。
- **影响：**用户无法从评分标准判断由谁、何时确认了当前版本；发生 JD 更新或争议时缺少可见审计上下文。
- **修复/验收：**在已确认版本显示确认人、确认时间和来源 JD 版本；新版本分别保留自己的确认信息，自动测试覆盖刷新及版本切换。

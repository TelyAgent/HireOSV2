# JD Management 评审会议总结：User Journey 与 AI 审查要求

来源：`/Users/apple/Desktop/Code_20261013201609.txt` 会议转写
日期：2026-10-13
用途：作为 JD Management User Journey、产品修复和 AI Review 的输入

> 说明：原始文件是语音转写，存在“创业阶梯”“bill manager”等识别误差。本文按上下文将其理解为职位/JD、Hiring Manager 或业务负责人；不确定事项单独列出，不把推测写成已确认规则。

## 1. 执行摘要

会议结论不是“基础流程没有实现”，而是“基础流程已通，但还没有形成可用的招聘工作闭环”。当前演示已覆盖职位库、新建职位、五种创建方式、Quick Start、语音/文字输入、AI 生成草稿和 JD 编辑；但产品缺少角色化任务、市场调研、权限分层、审批状态、截止时间和可恢复的交付闭环。

最重要的改进方向是：先定义角色和 User Journey，再让 AI 按角色审查每个页面。只把页面截图或代码交给 AI，无法发现“管理者要看哪些待审批岗位”“HR 何时发布”“面试官依据哪个版本面试”等业务问题。

## 2. 当前演示和已具备能力

演示路径大致为：职位库 → 新建职位 → 选择一种创建方式 → 输入招聘需求 → AI 在右侧 Workspace 生成草稿 → 修改 JD → 保存/继续编辑。

已看到的能力：

- 职位库展示已创建职位和基础状态；
- 职位支持增删查改；
- 新建职位 Copilot 提供五种创建方式；
- Quick Start 通过三个问题收集招聘意图；
- 支持语音和文字输入；
- AI 可生成职位草稿；
- 修改内容可被标记；
- 用户可以进入详情页编辑 JD。

会议认可五种创建入口比旧版本清晰，但指出五种入口最终都必须收集同一组必要业务信息，不能只做不同的输入形式。

## 3. 核心业务缺口

### 3.1 缺少市场薪资调研闭环

真实用户在填薪资前可能会问：北京、武汉等城市的 AI 产品经理市场薪资是多少？三年经验的候选人应给多少？当前预算是否合理？

期望流程是：提出市场问题 → AI 使用有授权的数据源调研 → 给出带地区、来源、日期的参考 → 用户确认内部预算 → 生成对外薪资范围 → 形成 Internal JD 和 External JD。

当前问题：

- AI 不能直接回答招聘市场问题；
- 必须先选中 JD 文本才能继续交互；
- 编辑模式和一般问答/调研模式没有区分；
- 调研结果不能自然写入结构化薪资字段；
- 用户可能离开系统去使用 ChatGPT，产品无法形成闭环。

### 3.2 三类信息的可见性没有落地

JD 至少需要区分：

1. 对内、对外都可公开的信息：职位名称、地点、部分职责、公开薪资等；
2. 仅内部可见的信息：实际预算、内部薪资上下限、招聘原因、编制、内部目标等；
3. restricted/敏感信息：只有 HR、Hiring Manager 或特定审批人可见的限制性要求。

页面需要明确字段的可见范围、可编辑者、确认者、发布者以及 AI 是否可以使用该字段。内部信息不能进入 External JD、公开搜索、邮件或无权限的 AI 上下文。

### 3.3 角色、任务和入口没有充分区分

不同角色登录后的目的不同：

- HR：补全 JD、协调、审批、发布和追踪交付；
- 管理者/Hiring Manager：确认为什么招、招什么人、何时发布、预算和关键取舍；
- 面试官：查看有效要求、准备面试、提交证据或建议；
- 最终审批人/Peer 面试官：按授权范围执行审批或评估。

同一个职位页面不能让所有角色看到相同信息和相同按钮。每个角色都应看到与自己相关的待办、截止时间、下一步和状态。

### 3.4 审批、确认、发布状态不完整

需要区分：

- 谁创建草稿；
- 谁修改内容；
- 谁可以确认；
- 谁可以审批；
- 谁可以发布；
- 哪个版本被批准；
- 哪个版本已经激活；
- 哪个版本已在渠道发布。

会议强调：只有具备相应权限的 HR 和 Hiring Manager/业务负责人才能执行最终确认或发布；其他角色的意见应作为评论或提案，不应静默改写正式标准。

会议还提到邮件审批超时自动生效，但“24 小时”还是“48 小时”尚未确认，不能直接实现为固定产品规则。

### 3.5 缺少截止时间和任务管理

仅显示最近更新时间不够。招聘岗位还需要展示：

- JD 完成截止时间；
- 计划发布时间；
- 当前负责人；
- 待谁审批；
- 是否逾期；
- 招聘何时应关闭或暂停；
- 下一步动作。

管理者进入系统首先应看到“待我审核、待我确认、急需发布、已超时”的岗位，而不是一个没有角色上下文的通用列表。

## 4. User Journey 的强制要求

每个角色的 User Journey 至少要写清楚：

1. 用户是谁、是什么角色；
2. 登录后的目的；
3. 登录进入哪个界面；
4. 用户要完成的业务目标；
5. 前置条件和岗位状态；
6. 具体操作路径；
7. 每一步关注的信息和需要做的决定；
8. 用户可见和不可见的内容；
9. 用户完成后的交接对象和版本化产物；
10. 失败、超时、权限不足和版本变化时的恢复路径；
11. 可验证的成功标准。

不能只写“点击某按钮”，也不能只描述页面功能。User Journey 必须表达用户进入页面时想做什么，以及页面如何支撑其完成目标。

## 5. AI Review 的两类标准

### 5.1 业务功能审查

AI 应按角色判断：

- 是否看到与自己有关的任务和岗位；
- 是否能找到待审核、待确认、待发布的项目；
- 是否具备必要字段和市场调研入口；
- 是否区分 Internal JD、External JD 和 restricted 信息；
- 是否区分 Draft、Approval、Activation、Publication；
- 是否显示截止时间、负责人、审批人和下一步；
- 是否把正确的版本/Snapshot 交给下一个角色；
- 是否在失败或未知结果时提供恢复路径。

### 5.2 应用性审查

每次 AI Review 必须强制检查：

- 是否容易理解和学习；
- 是否符合用户真实工作方式；
- 能一步完成的事情是否被拆成多步；
- 用户是否知道当前处于编辑、问答、调研还是审批模式；
- 页面是否给出清晰提示和下一步；
- 是否需要重复输入、重复跳转或重复确认；
- 角色看到的信息结构是否与其目标匹配；
- 页面是否足够简洁、可用，并符合 Google Workspace 风格的清晰层次。

## 6. 建议的 AI 审查流程

1. 为 HR、管理者、面试官等角色分别编写 User Journey；
2. 建立独立的 AI Review 标准 Markdown；
3. 将 User Journey、Review 标准和页面/代码作为同一组输入；
4. 按角色、按页面、按步骤进行审查；
5. 将发现的问题分为业务功能问题和应用性问题；
6. 转换为可执行开发任务；
7. 修复后重新按同一旅程回归验证。

优先审查 JD Management 的两个核心能力：

- 创建 JD；
- 管理 JD。

## 7. 优先修复事项

### P0

- 明确 HR、管理者、面试官登录后的首页和任务入口；
- 补齐角色、权限、确认、审批、发布和待处理状态；
- 补齐截止时间、负责人、下一步和逾期状态；
- 支持不依赖选中文字的招聘问答和市场薪资调研；
- 区分编辑模式、问答模式和调研模式；
- 明确内部、外部和 restricted 信息边界。

### P1

- 为五种创建方式建立统一的必填字段和缺口检查；
- 建立 Internal JD/External JD 的版本对比和发布前确认；
- 支持审批、拒绝、退回、超时和失败恢复；
- 为角色交接提供版本化产物和审计记录。

### P2

- 统一视觉和交互细节；
- 优化按钮提示、快捷切换和页面学习成本；
- 进一步完善 Google 风格的布局和信息层次。

## 8. 待确认事项

- 审批超时默认是 24 小时还是 48 小时；
- 自动生效是否适用于全部审批流；
- 各角色的最终权限矩阵；
- 薪资调研的数据源、引用和更新时间；
- 调研结果是否自动写入内部预算或必须人工确认；
- 哪些字段对外公开、仅内部可见或 restricted；
- JD 截止时间和发布时间是否为同一字段；
- 面试官能否编辑要求，还是只能评论/建议；
- “已招到人”由 JD 模块还是招聘管理模块维护。

## 9. 结论

会议要求产品从“功能能否跑通”转为“不同角色能否完成自己的招聘任务”。AI Review 的质量取决于输入是否包含角色、目的、路径、关注点、权限、交接和应用性标准；没有这些上下文，AI 只能做表面 UI 检查，无法发现关键业务缺口。

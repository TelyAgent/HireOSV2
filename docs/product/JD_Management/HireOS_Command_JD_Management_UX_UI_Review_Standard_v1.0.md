# HireOS Command — JD Management UX/UI 审查标准

文档编号：CMD-JD-UX-REVIEW-001

版本：v1.0

状态：AI Review 与人工验收共用标准

适用范围：JD Management 的职位库、创建职位、JD 编辑、审批、发布、任务与角色工作台

## 1. 目的与适用方式

本标准用于审查一个页面或一条完整操作路径是否真正支持用户完成招聘任务。审查不能只判断“页面是否好看”或“按钮是否能点击”，必须结合：

- 用户角色；
- 登录后的目标；
- 当前页面要完成的任务；
- 用户关注的信息；
- 权限与状态；
- 下一步和交接对象；
- 完成任务所需的实际证据。

每次 AI Review 都必须强制检查“应用性/可用性”。如果没有 User Journey、角色和业务目标，审查只能标记为“上下文不足”，不能直接给出“通过”。

本标准适用于：

1. 页面级审查：单个页面、弹窗、侧栏、空状态、错误状态；
2. 流程级审查：创建职位、补全 JD、审批、发布、版本变更；
3. 角色级审查：HR、管理者、面试官及其他授权角色；
4. AI 功能审查：问答、生成、修改、研究、提案、确认与外发。

## 2. 审查输入

审查开始前，必须准备以下输入：

| 输入 | 最低要求 |
|---|---|
| User Journey | 角色、登录目的、入口、目标、步骤、关注点、预期结果、交接对象 |
| 页面或流程 | 可访问的代码、原型、截图或录屏；最好包含完整操作路径 |
| 角色权限 | 可查看、可编辑、可确认、可审批、可发布的范围 |
| 业务状态 | 草稿、待审核、已批准、已激活、已发布、失败、未知等状态定义 |
| 任务上下文 | 截止时间、负责人、优先级、依赖和完成证据 |
| 设计基线 | Design Brief、组件规范、主题/字号/无障碍要求 |

若缺少其中任一项，报告必须在“审查限制”中明确说明，不得用推测补齐产品规则。

## 3. 审查工作方式

### 3.1 按用户旅程审查，不按页面孤立审查

每个页面都要回答：

1. 谁正在使用它？
2. 用户为什么来到这里？
3. 用户现在要完成哪一个业务动作？
4. 用户需要看见什么信息才能做决定？
5. 完成后要去哪一步？交给谁？
6. 如果失败、超时、权限变化或输入不完整，如何恢复？

### 3.2 每一步都要记录证据

对于流程中的每一步，记录：

| 字段 | 说明 |
|---|---|
| Step | 步骤编号和名称 |
| User action | 用户实际操作 |
| Expected outcome | 按 User Journey 预期看到的结果 |
| Evidence | 截图、DOM、录屏、状态、文案或代码位置 |
| Finding | 发现的问题或确认的优点 |
| Severity | P0 / P1 / P2 / P3 |
| Recommendation | 最小可行的修复方向 |
| Limitation | 无法从当前证据确认的内容 |

不能把“看起来应该可以”当作证据。截图只能证明可见状态，不能单独证明服务端权限、数据持久化、键盘可用性或真实交付结果。

## 4. 应用性/可用性硬性标准

以下十项每次都必须检查。任一 P0 问题未解决，流程不能判定为通过。

### U1. 容易理解

用户在首次看到页面时，能够理解：

- 当前所在的位置和对象是什么；
- 当前处于草稿、编辑、审批、发布还是查看状态；
- 页面服务的角色和任务是什么；
- 主要按钮会产生什么结果。

检查问题：

- 页面标题是否使用用户理解的业务语言；
- 是否明确显示 Job、版本、状态和当前负责人；
- “Save / Apply / Submit / Approve / Publish” 是否表达不同动作；
- 是否避免只显示技术词、内部模型词或无法理解的状态码；
- 是否避免把多个不同事实合并为一个“完成”状态。

失败示例：用户无法判断“已保存”是否意味着已批准或已发布。

### U2. 容易上手

用户无需培训或反复试错，就能知道从哪里开始。

检查问题：

- 首屏是否突出角色当前的下一步；
- 空状态是否给出清晰入口和示例；
- 创建职位的五种方式是否能帮助用户选择，而不是增加决策负担；
- 字段、按钮、输入框是否有清楚的标签和示例；
- 第一次使用时，是否有适量的说明而不是大段教程；
- 用户是否知道语音、文字、问答和文档编辑的区别。

失败示例：用户想咨询市场薪资，却必须先选中 JD 文本，才知道可以调用 AI。

### U3. 快速完成任务

页面应围绕用户目标组织信息和操作，减少等待、跳转和重复确认。

检查问题：

- 用户是否能在合理的最少步骤内完成主任务；
- 首要动作是否位于当前视线和合理的信息层级；
- 加载、保存、生成和提交是否提供及时反馈；
- 是否可以在当前上下文完成任务，而不被迫回到首页；
- 是否保留筛选、滚动位置、草稿和输入内容；
- 是否支持批量处理真正相同的动作。

硬性原则：能一步完成的事情，不应无业务理由拆成三步；必须拆分时，应说明每一步的决策价值。

### U4. 下一步明确

完成当前动作后，用户必须知道下一步该做什么、由谁做、何时完成。

检查问题：

- 页面是否显示 Next action；
- 是否显示负责人、截止时间、优先级和等待原因；
- 状态变化后主按钮是否随之变化；
- 是否能从任务、通知或审批深链回到正确版本；
- 任务完成是否有业务完成证据，而不只是 toast “Done”；
- 等待别人处理时，是否显示等待对象和可恢复动作。

失败示例：管理者看到一份 JD，但不知道是否需要审核、何时发布或应该交给谁。

### U5. 提示和按钮清楚

每个重要控件都要让用户知道“做什么、影响什么、完成后会怎样”。

检查问题：

- 主按钮是否只有一个最重要动作；
- 危险或不可逆操作是否有清楚的确认内容；
- 确认面板是否显示对象、版本、差异、渠道和影响；
- 禁用按钮是否解释原因，而不是只变灰；
- 错误提示是否说明问题、影响、修复方式和重试入口；
- AI 提案是否区分 Preview、Apply、Undo 和 Cancel。

不得使用含义模糊的按钮作为唯一入口，例如只显示“继续”“完成”“处理”。

### U6. 符合真实工作方式

系统应支持真实招聘工作，而不是要求用户适应不自然的界面流程。

检查问题：

- 用户能否先调研再填写薪资，而不是只能直接输入一个数字；
- 用户能否先提出问题，再决定是否修改 JD；
- 用户能否在一个工作区内查看需求、版本、审批和任务；
- 语音、文字、附件、链接和已有 JD 是否能进入同一条可追溯路径；
- 是否能区分内部 JD、外部 JD 和 restricted 信息；
- 是否支持现实中的协作、退回、改稿、审批、发布和撤回。

### U7. 信息结构符合角色目标

不同角色登录后应看到不同的重点信息，而不是所有人看到同一套页面。

| 角色 | 首要关注 |
|---|---|
| HR | 待补全、待审批、待发布、失败交付、负责人、截止时间 |
| 管理者 | 招聘目标、职责、预算/HC、待确认版本、发布时间、影响范围 |
| 面试官 | 当前有效要求、Requirement Snapshot、证据标准、我的面试任务、版本变化 |

检查问题：

- 首屏卡片是否与角色目标匹配；
- 列表列和筛选是否帮助用户完成任务；
- 是否优先显示待本人处理的事项；
- restricted 字段是否按字段权限隐藏，而不是只在视觉上遮盖；
- 是否避免向不需要的人展示无关信息和复杂配置。

### U8. 减少来回跳转、重复输入和重复确认

重复操作只有在带来明确的安全、权限或决策价值时才合理。

检查问题：

- 同一字段是否需要在多个页面重复录入；
- 用户从列表进入详情后返回，筛选和滚动是否保留；
- 用户是否需要在聊天、文档、审批页之间重复复制内容；
- 同一版本是否被要求多次确认；
- AI 重试是否会重复应用修改或重复发送邮件；
- 用户能否从错误位置直接回到修复位置。

如果系统必须跨页面，必须传递上下文：Job、版本、来源、未保存内容和下一步不能丢失。

### U9. 可恢复和可预期

用户遇到错误、网络中断、并发冲突或权限变化时，不能丢失工作，也不能误以为操作已成功。

检查问题：

- 加载、保存、生成、审批、激活、发布是否有独立状态；
- `outcome_unknown` 是否提供查询状态而不是默认重试；
- 失败是否保留输入并说明可恢复路径；
- 并发冲突是否显示 Base / Current / Your proposal；
- 权限撤销后是否停止展示敏感缓存；
- 重试是否幂等，不会重复创建版本、发送邮件或发布渠道。

### U10. 可访问、可读和可操作

本标准不能仅凭截图宣称完整无障碍合规，但每次审查至少检查：

- 信息和状态不只依赖颜色；
- 文字、按钮和表格在 200% 缩放下仍可用；
- 键盘可以到达主要操作，焦点顺序合理；
- 弹窗有清晰标题、焦点管理和关闭方式；
- 错误提示与输入字段关联；
- 加载、成功、失败和未知状态有可读文本；
- 字号切换不会隐藏主操作或破坏信息层级；
- 语音输入失败时有文字替代路径。

## 5. 功能与业务完整性检查

应用性审查必须与业务功能审查同时进行。至少检查以下内容：

### 5.1 角色与权限

- 登录后进入正确 Workspace 和角色工作台；
- 无权限 Job 不出现在列表、搜索、统计或摘要中；
- HR、管理者、面试官看到的字段、按钮和任务不同；
- @mention、评论或附件不会自动扩大权限；
- restricted 字段不会出现在外部 JD、搜索、导出、邮件或 AI 上下文；
- 读取、编辑、确认、审批、激活、发布权限分别校验。

### 5.2 必要字段和状态

至少核对：

- 职位名称、地点、职责、岗位要求、薪资范围、招聘人数；
- 负责人、工作模式、截止时间、计划发布时间；
- draft、pending review、approved、activation pending、published、failed、unknown；
- 当前版本、来源版本、更新时间和状态变化原因。

### 5.3 AI 交互边界

- AI 是否区分问答、研究、生成、修改和高影响动作；
- AI 是否能回答与岗位相关但不直接对应某段文字的问题；
- 市场调研是否显示来源、日期、地区和不确定性；
- AI 是否先展示 Proposed changes，再要求应用；
- AI 是否不会猜测 HC、币种、薪资周期、负责人、法律依据或受保护属性；
- AI 是否不会直接成为审批人或绕过人工确认。

### 5.4 版本、审批和发布

- Draft、Approval、Activation、Publication 是独立状态；
- 审批对象包含精确版本、差异、范围和内容 hash；
- 内容变更会使旧确认失效或创建新 revision；
- 批准不自动等于激活、open 或发布；
- 发布使用精确 external JD version 和渠道；
- 发布失败、撤下中和结果未知都有可恢复路径。

## 6. 信息架构与视觉检查

### 6.1 层级

页面信息顺序应优先满足：

1. 当前状态与下一步；
2. 用户需要做的决定；
3. 差异、风险和原因；
4. 具体字段和来源；
5. 历史、辅助信息和高级配置。

不应让装饰性图表、AI 分数或无关统计抢占主任务空间。

### 6.2 视觉一致性

检查：

- 主题、配色、字号、圆角、边框和阴影是否统一；
- Draft、Pending、Approved、Open、Published 是否不只依赖颜色；
- 表格、对话、差异、弹窗和 toast 是否使用一致的状态语言；
- 页面在常用桌面尺寸和 200% 缩放下是否不拥挤；
- 视觉重点是否与角色目标一致，而不是所有内容等权展示。

### 6.3 文案

文案应：

- 使用用户熟悉的招聘业务词；
- 明确动作和结果；
- 在错误中说明如何修复；
- 在禁用状态中说明缺少什么；
- 在 AI 结果中区分事实、建议、推测和来源；
- 避免“成功”“完成”“已处理”等无法说明业务结果的笼统词。

## 7. 严重级别与通过门槛

| 级别 | 定义 | 示例 | 处理要求 |
|---|---|---|---|
| P0 阻断 | 用户无法完成核心任务，或发生严重越权/错误外发 | 无法发布；面试官看不到必要要求；restricted 信息进入外部 JD | 必须修复后才能通过 |
| P1 高影响 | 主流程可绕行，但明显增加错误、时间或决策风险 | 没有下一步；审批版本不清；市场调研无法闭环 | 发布前修复或明确产品豁免 |
| P2 中影响 | 影响效率、理解或一致性，但存在可接受替代路径 | 重复输入；返回丢失筛选；提示不够清楚 | 进入近期修复队列 |
| P3 低影响 | 文案、间距、非关键视觉或增强项 | 标签不统一、次要对齐问题 | 可排入后续优化 |

判定规则：

- 存在 P0：不通过；
- 无 P0，但存在未豁免 P1：标记“有条件通过”，不得称为完成；
- 只有 P2/P3：可通过，但必须记录待办；
- 任何“无法从证据确认”的核心权限、持久化或交付结果：标记“未验证”，不等同于通过。

## 8. AI Review 输出格式

AI 每次审查必须输出以下结构：

```yaml
review:
  product: "JD Management"
  surface: "页面或流程名称"
  role: "HR | Manager | Interviewer | Other"
  journey_goal: "该角色本次要完成的业务目标"
  evidence:
    source: "截图 / 录屏 / DOM / code / prototype"
    steps_checked: [1, 2, 3]
  verdict: "pass | conditional_pass | fail | insufficient_context"
  findings:
    - id: "UX-001"
      severity: "P0 | P1 | P2 | P3"
      category: "clarity | learnability | efficiency | next_action | permissions | state | accessibility | ai_boundary"
      step: 2
      title: "一句话问题"
      evidence: "可观察证据"
      user_impact: "对角色目标的影响"
      recommendation: "最小修复方向"
      acceptance_check: "修复后如何验证"
  usability_check:
    understandable: "pass | fail | unknown"
    learnable: "pass | fail | unknown"
    efficient: "pass | fail | unknown"
    next_action_clear: "pass | fail | unknown"
    controls_clear: "pass | fail | unknown"
    real_workflow_fit: "pass | fail | unknown"
    role_information_fit: "pass | fail | unknown"
    no_unnecessary_hops: "pass | fail | unknown"
    recoverable: "pass | fail | unknown"
    accessible: "pass | fail | unknown"
  limits:
    - "截图无法证明的内容"
```

报告不得只写“体验一般”“交互不够友好”或“建议优化”。每条发现必须绑定：角色、旅程步骤、证据、影响、严重级别和验收方式。

## 10. 最低验收清单

在宣布页面或流程通过前，必须确认：

- [ ] 已指定具体角色和 User Journey；
- [ ] 首屏能支持该角色的登录目的；
- [ ] 页面明确显示当前对象、版本、状态和下一步；
- [ ] 主流程无需不必要的来回跳转、重复输入或重复确认；
- [ ] 必要字段、负责人、截止时间和等待原因可见；
- [ ] 权限、字段可见性和高影响动作符合角色授权；
- [ ] AI 的问答、研究、修改和外发边界清楚；
- [ ] 失败、未知、超时、并发和权限撤销都有恢复路径；
- [ ] 键盘、缩放、焦点、错误提示和非颜色状态至少完成基础检查；
- [ ] 所有 P0 已关闭，P1 已修复或有明确豁免；
- [ ] 每个结论都有证据，无法验证的内容已单独列出。

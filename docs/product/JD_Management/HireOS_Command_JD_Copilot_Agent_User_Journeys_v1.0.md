# HireOS Command — JD Copilot Agent 创建模块 User Journey

文档编号：CMD-JD-COPILOT-UJ-001  
版本：v1.0  
状态：基于 JD Copilot Agent PRD v0.2 的 User Journey 与 AI 审查输入  
范围：创建职位、完善草稿、质量分析、人工确认和提交审批

## 1. 文档目的与依据

本文将 [JD Copilot Agent PRD v0.2](HireOS_Command_JD_Copilot_Agent_PRD_v0.2.md) 转换为可执行的角色 User Journey。它用于：

- 说明不同角色登录后为什么进入 Agent 创建模块；
- 定义五种创建入口的共同目标、不同路径和完成条件；
- 检查 Agent 是否始终把控制权交还给用户；
- 为页面、原型和代码提供按角色的 AI Review 输入；
- 为后续可用性测试和验收测试建立基线。

本文不替代 PRD 的 API、数据模型和实现细节。产品行为以 PRD v0.2 为准；如果 User Journey 与 PRD 冲突，以 PRD 的状态、权限和人工确认要求为准。

## 2. Agent 创建模块的核心任务

Agent 的任务不是自动“写一篇 JD”，而是帮助用户把非结构化招聘意图转成可编辑、可追溯、可检查、可审批的职位草稿。

```text
进入 Create a Job
  → 选择创建方式
  → 输入招聘意图或材料
  → Agent 提取已知字段并标注来源/置信度
  → 追问关键缺失或冲突信息
  → 生成结构化 JD 草稿
  → 用户查看差异并逐项应用/调整
  → Analyze 检查完整性、一致性和风险
  → 用户保存草稿
  → 用户明确点击提交审批
```

Agent 必须遵守四个边界：

1. 建议默认不写入正式数据；
2. 应用修改、保存草稿、提交审批都需要用户显式操作；
3. 无法确认的信息标为待确认，不伪装成事实；
4. Agent 不自动审批、发布、撤回或发送外部通知。

## 3. 角色与权限

| 角色 | 登录后的主要目的 | 在 Agent 创建模块中的核心动作 | 不应自动获得的权限 |
|---|---|---|---|
| Recruiter / TA | 快速把招聘需求整理成合格 JD，并发起协作/审批 | 选择创建方式、补充字段、应用建议、保存草稿、提交审批 | 不能替审批人作出审批结论；不能绕过阻断项提交 |
| Hiring Manager | 补充职责、业务目标、能力标准和团队上下文 | 回答追问、编辑授权字段、确认岗位内容、处理业务冲突 | 不能修改未授权的预算/敏感字段；不能替 HR 或审批政策自动发布 |
| HR Approver | 确认内容、预算和风险已经处理 | 查看候选版本、差异、阻断项并批准或退回 | 不能把 AI 建议直接当成人工审批；不能在权限不足时查看 restricted 字段 |
| Viewer | 阅读职位草稿和 Agent 结论 | 查看授权内容、来源和分析结果 | 不能应用修改、保存草稿、提交审批或查看敏感字段 |

> 权限必须在动作执行时重新校验。聊天、附件、引用或 @mention 不能扩大用户的 Job、字段或用途权限。

## 4. 共同登录与入口旅程

### 4.1 登录目的

用户登录后，系统应让其快速回答：

- 我是否有权限创建或编辑职位？
- 我是在创建新职位，还是继续已有草稿？
- 我有哪些待处理的草稿、缺失项或审批任务？
- 当前用户能执行哪些动作？

### 4.2 共同路径

| 阶段 | 用户操作 | 预期结果 | AI/应用性检查 |
|---|---|---|---|
| 1. 进入 | 登录 → Job Library → Ask Copilot | 打开右侧 `Ask Copilot`，进入 `Create a Job` 首页 | 首页说明这是创建职位的任务，不把用户带入泛化聊天 |
| 2. 选择 | 查看五种并列入口，点击标题旁 `i` | 每个入口提供“是什么、适合什么、需要用户做什么”的提示条 | 用户无需培训即可选择适合自己的方式；入口没有隐含先后依赖 |
| 3. 开始 | 点击任一入口 | 所选方式先作为一条用户消息显示；Agent 立即以对话引导，不增加无意义配置页 | 点击后知道当前模式，底部输入提示随方式变化 |
| 4. 生成 | 输入文字、语音、文件、链接或表单 | 显示处理状态；输出字段、来源、置信度和缺失项 | 不把推断写成已确认事实；失败有重试或手工路径 |
| 5. 审阅 | 查看 Ask Copilot 与 Workspace 并列面板 | 草稿在 Workspace 预览；提案和字段差异可查看 | Agent 建议与正式文档视觉区分；不自动覆盖已有内容 |
| 6. 确认 | 用户逐项应用、保存或提交审批 | 每个高影响动作都有显式按钮和操作者记录 | 没有“自动完成”或模糊的 Done 状态 |

## 5. 五种创建方式 User Journey

五种入口形式不同，但最终都要形成结构化职位草稿，并遵循统一的来源、缺失、确认和权限规则。

### CJ-01 Quick Start：回答三个问题

**适用角色**：Recruiter、Hiring Manager   
**用户目的**：用户只知道招聘困难和目标，不知道如何组织成完整 JD。  
**输入方式**：文字或语音。

| 步骤 | 用户动作 | 预期结果 | 关注点 |
|---|---|---|---|
| 1 | 点击 `Quick Start` | Agent 一次性提出三个问题：遇到什么困难/为什么招人；希望候选人解决什么；必须具备哪些硬技能 | 不把三个问题拆成低效的逐题流程 |
| 2 | 一次回答全部或部分问题 | Agent 识别已回答内容，只追问未回答的问题 | 不重复询问已提供的信息 |
| 3 | 无法判断职位名称时回答 | Agent 追问应使用的 Job title，不留空或写 `New Role` | 推断必须可解释，不能伪造职位名称 |
| 4 | 完成关键回答 | 生成 1 份 JD 草稿，并在字段旁显示来源/置信度/待确认项 | 用户知道哪些是明确输入、哪些是 Agent 建议 |
| 5 | 在 Workspace 审阅 | 可查看概述、职责、要求、加分项、地点和工作方式 | 草稿未被视为正式职位 |
| 6 | 点击 `Create job from this draft` | 创建职位，创建者成为 Owner；刷新后数据仍在 | 创建动作必须是用户主动确认 |

**成功标准**：回答不完整时只追问缺失内容；生成一份可编辑草稿；未确认内容不伪装成事实；创建前没有审批/发布副作用。

### CJ-02 Start with a Job Title：从职位名称开始

**适用角色**：Recruiter、Hiring Manager   
**用户目的**：用户知道职位名称，希望快速比较不同表达风格。

| 步骤 | 用户动作 | 预期结果 | 关注点 |
|---|---|---|---|
| 1 | 点击 `Start with a Job Title` | Agent 只展示引导文案，底部输入框聚焦 | 不额外弹出第二个输入框 |
| 2 | 输入职位名称 | 生成 3 份 JD：Concise & direct、Warm & people-first、Detailed & structured | 职位名称在对话中只出现一次 |
| 3 | 对比卡片或 Workspace 页签 | 三份内容风格不同，但核心事实一致 | 不以风格差异掩盖事实差异 |
| 4 | 选择一个版本 | 当前选择明确显示，Workspace 与对话卡片联动 | 用户能知道最终将创建哪一版 |
| 5 | 可选地 Refine | 对所有版本提出的统一修改被高亮 | 修改不应悄悄只作用于未选版本 |
| 6 | 点击 `Create job with version A/B/C` | 使用所选版本创建职位并进入编辑页 | 创建前仍需用户确认 |

**成功标准**：只有该入口生成三份版本；用户选择的版本与最终创建版本一致；三份版本不存在无来源的事实扩散。

### CJ-03 Upload a JD：上传已有 JD

**适用角色**：Recruiter、Hiring Manager   
**用户目的**：已有 PDF/DOCX/TXT，希望快速结构化和完善。

| 步骤 | 用户动作 | 预期结果 | 关注点 |
|---|---|---|---|
| 1 | 点击 `Upload a JD` | 立即打开文件选择器，同时显示引导和 `Choose file` | 不增加无必要配置步骤 |
| 2 | 取消或重新选择 | 取消不报错，可再次打开 | 失败和取消路径可恢复 |
| 3 | 选择支持的文件 | Agent 提取标题、职责、要求、加分项、地点和工作方式，生成 1 份草稿 | 每个字段带来源；文件原文不直接成为正式数据 |
| 4 | 文件无法读取 | 显示明确失败原因，并提供手动输入/重试 | 不生成空草稿或编造内容 |
| 5 | 审阅并确认 | 用户可逐项应用建议，查看原文与改写差异 | AI 不覆盖用户原有内容 |

**成功标准**：支持格式处理路径清楚；无法解析时可恢复；来源、置信度和差异完整；不会因上传完成而自动保存或提交审批。

### CJ-04 Paste a Link or Text：粘贴链接或文案

**适用角色**：Recruiter、Hiring Manager   
**用户目的**：已有外部职位链接、JD 正文或会议笔记，希望转为公司内部草稿。

| 步骤 | 用户动作 | 预期结果 | 关注点 |
|---|---|---|---|
| 1 | 点击入口 | Agent 提示粘贴链接或完整文案，底部输入提示更新 | 用户知道链接和正文都被支持 |
| 2 | 粘贴过短或无法识别内容 | 提示重新粘贴，不把内容当成有效 JD | 错误提示解释如何修复 |
| 3 | 粘贴链接 | 显示来源链接、公司/职位、可用性和读取状态 | 不声称已抓取未读取的页面 |
| 4 | 粘贴正文/会议笔记 | 提取并改写为 1 份结构化草稿 | 保留来源类别，不能把推断当明确要求 |
| 5 | 页面无法访问或来源不可靠 | 明确提示无法读取/来源不可靠，提供手动输入 | 不编造外部页面内容；遵守版权边界 |
| 6 | 审阅并确认 | 用户查看“原始来源 → 新草稿”的差异后应用 | 对外部内容只能合理改写，不大段复制 |

**成功标准**：链接和正文识别规则可理解；来源和失败状态可追踪；不能读取的页面不会产生虚假草稿。

### CJ-05 Create Manually：手动创建

**适用角色**：Recruiter、Hiring Manager  
**用户目的**：用户希望逐字段控制，不使用 AI 起草。

| 步骤 | 用户动作 | 预期结果 | 关注点 |
|---|---|---|---|
| 1 | 点击 `Create Manually` | 对话中展示表单，不调用 AI 起草 | 用户知道这是手动路径 |
| 2 | 填写必填项 | 必填为 Job title、Location、Headcount、Responsibilities、Requirements | 字段名称和业务含义清晰 |
| 3 | 留空或输入非法值 | 对应字段标红并提示；不创建职位 | 服务端也应复核，不只依赖前端 |
| 4 | 填写可选项 | 可补充 Level、Work model、Department、Reports to、薪资范围/周期 | 选填不应伪装成已确认事实 |
| 5 | 点击 `Save` | 直接创建职位并进入编辑页，不经过 Workspace 预览 | Save 是用户明确动作 |
| 6 | 打开 Analyze | 完整性检查指出概述等仍缺失的字段 | 手动创建不绕过统一质量门禁 |

**成功标准**：表单内容原样进入对应章节；非法数据无法创建；手动创建仍受完整性和审批前置条件约束。

## 6. 创建后的完善、分析和审批旅程

### CJ-06 完善已有草稿

**主角色**：Recruiter / Hiring Manager  
**目标**：在已有草稿上提出修改，但不丢失旧内容和审计记录。

1. 用户打开职位编辑页右侧 `Copilot`；
2. 用户可以直接提问或引用选中文字，例如“把职责改得更偏 B2B 增长”；
3. Agent 返回可审阅的新增/替换/润色建议和 old → new diff；
4. 用户选择逐项 `Apply`、编辑提案或撤销；
5. 应用后记录操作者、时间、来源和 revision；
6. 未点击应用前，正式 JD 不改变；
7. 用户无权限时只能查看结论或请求有权限的人处理，不显示伪可用按钮。

**应用性要求**：编辑模式必须明确显示；如果用户提出的是市场调研或一般招聘问题，应允许切换到问答/调研路径，而不是强迫用户先选中文字。

### CJ-07 提交前 Analyze

**主角色**：Recruiter；协作者可查看结果。  
**目标**：判断草稿是否达到提交审批条件。

| 阶段 | 用户动作 | 预期结果 |
|---|---|---|
| 1 | 点击 `Analyze` | 显示处理中状态，完成后自动切到 `Analysis` 标签 |
| 2 | 查看分析 | 分为 `阻断`、`需要确认`、`优化建议`；显示缺失字段、冲突、文案风险和流程前置 |
| 3 | 处理阻断项 | 用户补填或逐项使用 `AI fix`；每项显示修复前后差异 |
| 4 | 处理需要确认项 | 用户确认或保留 Unknown；不允许 Agent 替用户确认敏感事实 |
| 5 | 查看建议 | 可选择应用；建议不阻断保存 |
| 6 | 尝试提交审批 | 阻断项未解决时 `Submit for approval` 不可用并说明原因 |

检查至少覆盖：职位名称、地点、HC、概述、职责、要求、可见范围、JD ID、语言版本，以及职级/年限、地点/工作方式、HC/审批状态的一致性。

### CJ-08 保存草稿与提交审批

**主角色**：Recruiter；HR Approver 后续处理。  
**目标**：明确区分保存和提交，不让 Agent 自动触发高影响动作。

1. Recruiter 点击 `Save draft`；系统记录操作者、时间、来源和 revision；
2. 系统保持草稿状态，不发送审批或发布通知；
3. Recruiter 点击 `Submit for approval`；系统重新校验权限和阻断项；
4. 系统展示提交的精确版本、未处理项、审批人和影响；
5. Recruiter 显式确认后创建审批任务；
6. HR Approver 查看候选版本、差异、风险和来源；
7. Approver 选择批准或退回，并留下人工决策记录；
8. Agent 不得替 Approver 点击批准，也不得自动发布。

## 7. 角色交接

| 交接 | 发起者 | 接收者 | 交接对象 | 必须保留 |
|---|---|---|---|---|
| 招聘意图 → 草稿 | Hiring Manager / Recruiter | Recruiter | 结构化字段、来源、置信度、Unknown | 原始输入和未确认项 |
| 草稿 → 业务确认 | Recruiter | Hiring Manager | JRP 草稿、职责、要求、成功标准、冲突 | old → new diff、来源和变更人 |
| 草稿 → 审批 | Recruiter | HR Approver | 冻结版本、Analysis、阻断项、可见范围 | 版本、操作者、时间和审批策略 |
| 审批结果 → 后续编辑 | HR Approver | Recruiter | Approved / changes requested / rejected | 决策人、理由和精确版本 |
| Viewer 阅读 | 任何有权限角色 | Viewer | 授权 JD 和 Agent 结论 | 字段权限和不可见内容不泄露 |

## 8. AI Review 输入与验收标准

AI 审查每个页面时应同时获得 User Journey、当前角色和页面状态，不应只看截图。

```yaml
journey_id: CJ-01
module: JD Copilot Agent - Create a Job
role: Recruiter | Hiring Manager | HR Approver | Viewer
goal: "角色登录后希望完成的业务结果"
entry: "登录后的页面、Job Library 或编辑页入口"
mode: create | edit | analyze | approval | viewer
preconditions:
  - "权限、职位状态、已有材料或草稿"
steps:
  - id: 1
    user_action: "用户动作"
    expected_ui: "可观察页面、卡片、状态或按钮"
    decision: "用户需要判断什么"
    permission_check: "允许/拒绝的字段和动作"
    recovery: "失败、取消、超时或无权限时的路径"
agent_check:
  - "来源、置信度、Unknown、diff、确认边界"
success_criteria:
  - "可验证的完成结果"
open_questions: []
```

### AI Review 必查项

1. 角色是否知道自己为什么进入 Create a Job，以及当前模式是什么？
2. 五种创建入口是否容易理解，是否没有额外且无意义的中间步骤？
3. Agent 是否只追问缺失信息，并支持一次回答多个问题？
4. 生成内容是否区分用户明确输入、来源材料、Agent 推断和建议？
5. 用户是否能在不选中文字的情况下提出招聘相关问题；编辑/问答/调研模式是否清楚？
6. Agent 是否在应用、保存和提交审批前交还控制权？
7. 是否清楚显示 diff、来源、置信度、版本、操作者和时间？
8. 阻断、需要确认和优化建议是否区分；阻断是否真的阻止审批提交？
9. 上传、链接、语音和解析失败是否可理解、可恢复且不编造结果？
10. 不同角色是否只能执行授权动作，Viewer 是否不会看到敏感字段或伪按钮？
11. 是否存在任何未经人工确认的审批、发布、撤回或外部通知？
12. 用户能否一步完成的动作是否被拆成多步；页面是否提供清晰下一步？

## 9. MVP 完成标准

- 五种创建方式均可从 `Create a Job` 首页进入，并完成草稿或保存职位；
- Quick Start 只追问未回答的问题；职位名称无法推断时明确追问；
- Start with a Job Title 生成三份可比较版本，其他入口生成一份；
- 上传和链接失败有可恢复路径，不生成虚假内容；
- 手动表单校验必填字段和非法值，保存不经过 AI 起草；
- 草稿、已有 JD 修改和 AI 修复均以建议/diff 呈现，未确认前不写入；
- Analyze 区分阻断、需要确认和优化建议；阻断项存在时不能提交审批；
- 保存草稿、提交审批和应用修改均需要用户显式点击；
- Agent 不自动审批、发布、撤回或发送外部通知；
- 每次建议和应用操作均保留来源、时间、操作者和 revision；
- 语音、文件、链接、权限、网络和解析异常不会导致用户丢失可恢复输入。

## 10. 待确认项

以下问题来自 PRD v0.2，本 User Journey 不替产品做决定：

- AI 默认值是否需要在界面显式标注为“默认”；
- PDF/DOCX 的真实解析能力和失败标准；
- 粘贴正文识别阈值是否固定为 60 字符或 3 行；
- 外部链接抓取的授权、版权和来源保留规则；
- 无法推断职位名称时是否一律追问；
- Viewer 是否可以评论或只读；
- 允许使用哪些历史 JD、模板和公司画像；
- 市场薪酬调研与对标 JD 能力属于 P1，是否纳入本轮 Agent 入口；
- 提交审批的具体阻断规则和审批政策版本。

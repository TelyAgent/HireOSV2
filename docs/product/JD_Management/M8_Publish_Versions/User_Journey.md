## 角色与权限（公共，摘自 [九模块 User Journey §0.1](../HireOS_Command_JD_Management_Module_User_Journeys_v1.0.md)）

| 角色 | 登录后的主要目的 | 核心操作 | 默认限制 |
|---|---|---|---|
| Recruiter / TA | 将招聘需求整理成合格 JD，协调协作者并推动审批/交付 | 创建职位、补全字段、应用 AI 建议、保存草稿、提交审批、追踪发布 | 不能替审批人作出审批结论，不能绕过阻断项提交或发布 |
| Hiring Manager | 说明为什么招、招什么人、成功标准和团队上下文，并确认业务取舍 | 回答追问、编辑授权字段、解决冲突、确认岗位内容、参与审批 | 不能修改未授权预算/敏感字段，不能自动替代 HR 或审批政策发布 |
| HR Approver | 确认内容、预算、风险和流程前置条件已经处理 | 查看候选版本、差异、风险和影响，批准、退回或拒绝 | 不能把 AI 建议当成人工决策；无权限时不能查看 restricted 字段 |
| Viewer | 阅读获授权的 JD、分析结论和当前有效版本 | 查看职位、来源、版本和授权的 Agent 结论 | 不能应用修改、保存、提交审批、发布或查看敏感字段 |

> 2026-10-14 用户决定：采用以上四个角色，并恢复审批流程。这替代了 [#15](https://github.com/JsonSuCoder/HireOSV2/issues/15) 的三档权限和 [#9](https://github.com/JsonSuCoder/HireOSV2/issues/9) 中“去掉审批”的部分。审批流程目前后端没有实现，相关用例在实现前标记为 known gap。

# 旅程

**主角色**：Recruiter / TA（发布）；HR Approver（发布前审批，见 M7）
**登录目的**：把合格的 JD 发布出去，之后的修改可以追溯、对比，必要时能回到旧版本。
**入口**：职位编辑页 → Publish；页头 → Version history

## 输入

| 类型 | 内容 |
|---|---|
| 前置数据 | 一份全部合格且冻结版本有有效批准结果的草稿（seed，或 M6/M7 的结果），含 Public / Internal / Confidential 三种块；批准可来自 HR Approver 人工决定或 M7 的 24 小时系统超时决定 |
| 用户数据 | 版本说明；修改一条要点；修改某块的可见范围 |
| 外部依赖 | 当前 Publish 仅生成内部版本，不依赖渠道；渠道发布与撤回属于后续阶段 |

## 流程

```mermaid
flowchart TD
  P[点击 Publish] --> G{门禁：必填全部合格?}
  G -->|否| X[按钮不可用，服务端也拒绝]
  G -->|是| D[发布窗口：JD ID、新版本号、版本说明<br/>说明仅生成内部版本]
  D --> C[确认]
  C --> V1[(生成不可变版本 v1<br/>页头版本徽章更新，活动记录)]
  V1 --> E[修改内容]
  E --> U[页头显示 Unpublished changes<br/>当前有效内部版本仍是 v1]
  U --> P2[再次 Publish：列出相对 v1 的变更]
  P2 --> V2[(v2)]
  V2 --> H[Version history：对比任意两版]
  H --> R[恢复 v1]
  R --> N[(草稿回到 v1 内容<br/>历史不删除，新增恢复记录)]
```

## 步骤

| # | 用户意图与操作 | 系统反馈 | 用户需要判断 |
|---|---|---|---|
| 1 | 点击 Publish | 窗口显示 JD 唯一 ID（JD-年份-编号）、新版本号、可选说明；明确只生成内部版本、不会对外发送 | 是否生成这个版本 |
| 2 | 填说明并确认 | 生成内部 v1；版本徽章更新；活动记录新增一条 | — |
| 3 | 打开对外页面（后续渠道阶段） | 只有 Public 内容；没有 Internal 和 Confidential | 对外内容是否合适 |
| 4 | 修改一条要点 | 页头出现 `Unpublished changes`；当前有效内部版本仍是旧内容 | — |
| 5 | 再次 Publish | 版本号 +1；窗口列出本次相对上一版的变更 | 变更是否都要发布 |
| 6 | 版本页对比两版 | 显示新增、删除、修改、可见范围变化 | — |
| 7 | 恢复到旧版本 | 草稿回到旧版内容；历史版本保留；新增恢复记录 | — |
| 8 | 撤回测试渠道（后续渠道阶段） | 对外页面下线，记录撤回时间 | — |

## 异常与恢复

| 场景 | 预期 |
|---|---|
| 双击 Publish | 只生成一个版本（幂等键） |
| 渠道超时或无回执 | 显示结果未知，主操作是查询状态，不默认重发 |
| 发布时网络断开 | 不显示成功；恢复后可以查询实际结果 |

## 输出与交接

| 输出 | 内容 |
|---|---|
| 持久化 | JobDocumentVersion（版本号、内容哈希、发布者、时间、说明）；Job 状态 draft→published（Core 为 open）；JD 唯一 ID。历史 Published 无版本职位补为 v1；找不到原发布快照时，以现有 JD 内容生成并标记“迁移基线”，不伪造未知原审批和发布时间 |
| 记录 | 本阶段活动记录：内部版本发布、恢复、历史 v1 补录；渠道撤回留待后续 |
| 交接 | 本阶段给下游（筛选/面试）引用精确的内部版本号；后续渠道阶段的对外内容只取精确版本中的 Public 块 |

**禁止副作用**：Internal/Confidential 内容出现在对外页面；修改已发布的版本内容；恢复时删除历史；不合格时服务端放行发布。

**成功标准**：每次成功 Publish 生成新的不可变内部版本；内容未变仅改说明不生成版本；历史可追溯、可对比、可恢复。对外 Public 过滤属于后续渠道阶段。

**测试映射**：闭环 F1、E1、E2、E4（部分）；线上问题 F-005、F-013。

**待确认**：邮件审批的异常反馈及额外通知细节（M7）。后端恢复接口是否存在由工程核查。M7 已决定仅 HR Approver 一步人工审批，登录后可批准、退回或拒绝；24 小时未决时允许系统批准冻结版本，两种来源都必须明确记录。

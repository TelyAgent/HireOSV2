## 1. 背景与目标

已批准的 JD 需要发布出去；之后的修改要能追溯、对比，必要时回到旧版本。对外只能出现可公开的内容。

**目标**：每次发布生成不可变的新版本，对外只含 Public 内容；历史可追溯、可对比、可恢复。

## 2. 范围

| 包含 | 不包含 |
|---|---|
| 发布窗口、仅生成内部新版本、JD 唯一 ID | 第三方招聘渠道适配器、对外发布与撤回（线上暂无渠道） |
| 未发布修改提示 | 对外邮件发送 JD（M7 的审批邮件不在本模块） |
| 版本历史、两版对比、恢复旧版本 | 暂停、关闭、归档（建议的 M11） |
| 历史 Published 无版本职位补成 v1 | 渠道状态、超时回执与撤回（后续阶段） |

## 3. 功能需求

| ID | 需求 |
|---|---|
| FR-1 | Publish 按钮仅在 Ready 且冻结版本有有效批准结果时可用：HR Approver 人工批准，或 M7 规定的 24 小时未决系统批准 |
| FR-2 | 发布窗口显示 JD 唯一 ID（`JD-年份-编号`）、新版本号、可选版本说明，并明确本阶段仅生成内部版本，不向渠道发送 |
| FR-3 | 每次成功 Publish 生成一个新的不可变版本（首次为 v1，此后递增）；页头版本徽章更新；活动记录新增一条 |
| FR-4 | 发布后修改内容，页头显示 `Unpublished changes`；当前有效内部版本仍是旧版本 |
| FR-5 | 再次发布时，窗口列出相对上一版的变更 |
| FR-6 | 版本页可以对比任意两个版本：新增、删除、修改、可见范围变化 |
| FR-7 | 恢复旧版本：草稿回到旧版内容，历史版本保留，新增一条恢复记录 |
| FR-8 | 历史上职位状态为 Published、但无 JobDocumentVersion 的职位统一补为 v1；若无原发布快照，以现有 JD 内容生成 v1 并标记“迁移基线”；不得伪造原审批和发布时间 |
| FR-9 | 后续接入渠道时：每个渠道独立记录状态；超时或无回执先查询，不自动重发；撤回需记录时间 |

## 4. 业务规则

| ID | 规则 |
|---|---|
| BR-1 | 已发布的版本内容不可修改 |
| BR-2 | 本阶段 Publish 只生成内部版本，不执行对外发送；后续对外内容只能包含 Public 块，Internal 和 Confidential 不进入对外页面、导出或渠道 |
| BR-3 | 发布引用精确的已批准版本和批准来源（人工 / 系统超时），不引用“最新版” |
| BR-4 | 发布后修改内容需重新提交审批，批准后才能再次发布 |
| BR-5 | 恢复旧版本不删除任何历史，恢复结果作为新草稿，需重新审批后发布 |
| BR-6 | 双击 Publish 只生成一个版本（幂等） |
| BR-7 | 渠道结果未知时不默认重发，先查询 |
| BR-8 | 服务端再次校验门禁，不合格或未批准的发布请求被拒绝 |
| BR-9 | 内容未变而仅修改版本说明时不得 Publish，也不得因此生成新版本 |

## 5. 数据

| 对象 | 关键字段 |
|---|---|
| JD 唯一 ID | `JD-年份-编号`，每个职位一个 |
| JobDocumentVersion | 版本号、内容哈希、发布人、时间、说明、对应审批决定 |
| 发布记录 | 本阶段记录内部版本发布；渠道状态和外部 ID 留待渠道阶段，不得把内部 Publish 当作已对外发布 |
| Core Job | status：draft → published（Core 为 open） |
| 活动记录 | 本阶段：内部版本发布、恢复、历史 v1 补录；渠道撤回留待后续 |

## 6. 权限

| 角色 | 能做 |
|---|---|
| Recruiter / TA | 发布已批准版本、查看版本、对比、恢复（恢复后需重新审批） |
| Hiring Manager | 查看版本和对比；不能发布 |
| HR Approver | 审批（M7）；查看版本 |
| Viewer | 只看当前有效版本 |

## 7. 非功能要求

- 本阶段 Publish 不发送到渠道；测试在隔离职位上验证内部版本，不执行对外发布。后续渠道测试才适用“只用测试渠道、发布后立即撤回”（测试脚本 v0.1 §1.2）。

## 8. 验收标准

| ID | 验收 | 对应闭环路径 |
|---|---|---|
| AC-1 | 无有效批准结果或未 Ready 时不能发布，服务端也拒绝；有效批准可来自 M7 人工决定或 24 小时系统超时决定 | P1、P2 |
| AC-2 | 成功 Publish 每次生成递增新版本；窗口显示 JD ID、新版本号、说明和“仅内部版本”影响范围，活动记录可查 | P3 |
| AC-3 | 本阶段 Publish 不产生渠道发送或外部发布记录；后续渠道上线再验对外只含 Public | P13；P4（后续） |
| AC-4 | 修改后显示 Unpublished changes，当前有效内部版本内容不变 | P5 |
| AC-5 | 两版对比正确；恢复不删历史 | P6、P7 |
| AC-6 | 双击只生成一个版本 | P8 |
| AC-7 | 内容未变、仅修改版本说明不能生成新版本 | 新增 |
| AC-8 | 历史 Published 无版本职位补为 v1；无原快照时使用现有 JD 内容并标记“迁移基线”，不伪造未知审批和原发布时间 | 历史数据 |
| AC-9 | 渠道超时显示结果未知（渠道阶段验收） | P9（后续） |

## 9. 依赖与实现

- 后端：`GET jobs/:jobId/versions`、`POST jobs/:jobId/publish`、`PATCH jobs/:id/status`（draft / published）。
- 依赖 M7 的审批结果（人工 HR Approver 一步，或符合规则的 24 小时系统超时批准）；邮件审批按钮的决定回传也是 M7 结果来源。
- 发布渠道不属于本阶段 Publish；后续渠道阶段另行验收。

## 10. 待确认

1. 后端是否已有恢复接口（工程核查，不是产品规则待决）。
2. 邮件审批结果回传失败、重复或过期的反馈细节，见 M7。

> 2026-10-15 用户决定：Publish 当前只生成内部版本；每次成功 Publish 生成新版本；历史 Published 无版本职位统一补为 v1，缺原快照时以现有 JD 内容生成并标记迁移基线；内容未变、只改版本说明时不允许 Publish。恢复旧版本后需重新审批已由 BR-5 规定，不再列为待确认。

# HireOS Command — JD Management 用户旅程与测试脚本

Doc ID: CMD-JD-UJ-001  
Version: v0.2（测试环境改为**已发布上线的链接**）  
Scope: JD Management 模块（创建职位、编辑与检查、发布、权限、版本）  
状态: 线上功能仍在开发中，**暂不执行旅程**；其中 J7（权限）因权限角色未实现暂缓，J8（发布）因线上暂无发布渠道暂缓真实发布。  
用途: 用标准的用户旅程驱动测试。每条旅程既是“用户怎么用”的描述，也是可逐步执行、逐步打勾的测试脚本。

依据文档：`JD Copilot Agent PRD v0.2`（创建方式、入口与默认值）、`JD 完整性标准 v0.1`（必填、待修改规则）。**预期结果以这两份文档为准，而不是以线上当前表现为准**，这样线上与文档不一致的地方才会被测出来。

> 与原型测试的关键区别：线上是真实数据、真实账号、真实 AI 与真实文件解析。数据不会因刷新而重置，AI 输出每次可能不同，**发布会产生对外可见的结果**。因此本文档在数据准备、预期结果写法和安全约束上与原型版不同，见第 1、2 节。

## 1. 使用方法

### 1.1 测试环境（执行前填写，并随缺陷一起记录）

| 项 | 内容 |
| --- | --- |
| 线上地址 | `https://hireos.aipollo.me/hireos/jd/jobs` |
| 版本 / 构建号 | `{BUILD}`（页面底部、设置页或发布说明里查；查不到就写发布日期） |
| 测试日期 | |
| 浏览器与版本 | 至少 Chrome 最新版；有条件再加 Safari、Edge |
| 语言 | English / 中文 各跑一遍 J1 与 J9 |
| 测试人 | |

### 1.2 数据与安全约束（必须遵守）

1. **所有测试职位名称加前缀 `[UJ-TEST]`**，例如 `[UJ-TEST] J1 Growth Operations Manager 1012`，避免混入真实职位，也方便清理。
2. **不使用真实候选人、真实薪资或真实公司机密作为测试内容。**
3. **J8 会真实发布**：线上目前**没有发布渠道**，所以需要真实发布的步骤暂缓，等渠道上线后再执行；届时只选测试渠道，发布后立即撤回并记录撤回时间，**不要在 LinkedIn 等对外渠道上做发布测试。**
4. 每条旅程都新建自己的职位，不复用上一条旅程的职位；旅程之间不依赖对方的数据。
5. 测试完成后，把所有 `[UJ-TEST]` 职位归档或删除，并把清理结果写进测试记录。
6. 线上数据不会重置，所以“前置条件”里需要的状态（例如“缺少必填项的职位”）都要在旅程开头**自己制造**，第 5 节每条旅程已写明准备步骤。

### 1.3 执行与记录

1. 用测试账号登录（见第 3 节）；需要换角色时退出后用另一个账号登录，不要用同一个浏览器同时登录两个账号。
2. 按旅程逐步执行，对每一步的“预期结果”标记 ✅ 通过 / ❌ 失败 / ⚠️ 部分通过。
3. 失败的步骤按第 6 节的模板记录缺陷，写明依据（文档章节）、环境与构建号。
4. 全部跑完后，用第 7 节的覆盖矩阵检查有没有漏测的需求。

## 2. 旅程的写法（模板）

每条旅程固定包含下面 7 块，写新旅程时照着填：

| 块 | 写什么 | 注意 |
| --- | --- | --- |
| 编号与名称 | J 编号 + 一句话目标 | 名称写用户目标，不写功能名 |
| 优先级 | P0 主流程 / P1 重要分支 / P2 边界与异常 | P0 必须每次发版后回归 |
| 角色 | 谁在做（对应一个测试账号） | 一条旅程只围绕一个主角色，换角色就写新的步骤段 |
| 前置条件与数据准备 | 账号、权限，以及要先制造出来的数据 | 线上不能依赖“示例数据”，要写清怎么造 |
| 测试数据 | 输入的文字、文件、链接 | 给出可直接使用的内容 |
| 步骤表 | `步骤 / 用户操作 / 预期结果 / 依据` | 一步只做一件事；预期结果写“看得见的现象” |
| 通过标准 | 整条旅程怎样算通过 | 例如“发布按钮的状态始终与必填合格一致” |

写预期结果的原则：

- **可观察、可判定**：写文案、数字、状态（可点 / 不可点 / 显示 / 隐藏）。
- **有出处**：每一步标注依据；没有出处的写“待确认”，并记为文档缺口。
- **AI 输出写“判定条件”，不写“固定文字”**：线上 AI 每次的措辞可能不同，所以不要写“生成的概述是 xxx”，而写“概述为 2–4 句、包含职位名称、不含来源说明、没有编造的数字”。同一输入至少跑 2 次，确认都满足判定条件。
- **加入线上才有的检查**：数据刷新后仍在（持久化）、服务端校验（不能只靠前端拦截）、加载与失败状态、响应时间。

## 5. 旅程详情

### J1 用 Quick Start 回答 3 个问题创建职位（P0）

**前置条件**：账号 A 已登录，在职位列表页。无需准备数据。  
**测试数据**：Q&A 回答（英文，三行）。

| 步骤 | 用户操作 | 预期结果 | 依据 |
| --- | --- | --- | --- |
| 1 | 点击 **Ask Copilot** | 打开右侧面板；标题 `Ask Copilot`；主标题 `Create a Job`，副标题 `Choose how you’d like to start.`；5 个入口并列，每个只有标题 + 一句话，标题右侧有小 “i” | PRD 5.1 |
| 2 | 点击 Quick Start 标题旁的 “i” | 弹出提示条，写明是什么、适合什么、你要做什么；**没有进入该入口** | PRD 5.1 |
| 3 | 点击 **Quick Start** | 先出现你的消息 `Quick Start`，随后 agent 的**一条消息同时列出 3 个问题**（困难、希望候选人解决的问题、必备硬技能）；底部输入框聚焦 | PRD 5.1 |
| 4 | 只回答前两行后发送 | agent 只追问第 3 个问题，不重复问前两个 | PRD 5.1 / FR-2 |
| 5 | 回答第 3 行并发送 | 有“正在生成”的反馈；生成 **1 份**草稿（不是 3 份）；右侧展开 Workspace，与 Ask Copilot 并列；职位名称由回答推断，合理且不为空、不是 “New Role” | PRD 5.1 |
| 6 | 检查草稿内容（判定条件） | 概述 2–4 句、含职位名称；职责 ≥ 3 条且以动词开头；要求含你回答的硬技能；没有来源说明类文字；没有回答里不存在的编造数字 | 标准 B1、C1、D1 |
| 7 | 发送 `add TikTok growth experience and make it remote` | Workspace 里改动处高亮；工作模式变为 Remote；你的消息在对话里只出现一次 | PRD 5.1 共同规则 |
| 8 | 点击 **Create job from this draft** | 跳转到该职位的编辑页；出现创建成功提示；**刷新页面后职位仍在**，职位列表里能看到 | PRD 5.1；持久化 |
| 9 | 查看标题下字段行 | 始终显示 Location、Headcount、Workplace type；未提供时 Location 为 `Ho Chi Minh City, VN`、Headcount 为 `1`；Workplace type 为 Remote；Level 不显示 | PRD 5.2 |
| 10 | 点击 **新对话**，再选 Quick Start，点麦克风（首次会请求麦克风权限） | 允许权限后能真实转写你说的话；转写完成后自动发送；拒绝权限时有清楚的提示，不崩溃 | PRD 5 侧边栏组成 |

**通过标准**：全程无报错；每个入口点击后立即进入对话引导；创建的职位字段符合 PRD 5.2；数据刷新后不丢。  
**常见失败点**：用户消息重复；三个问题被一题一题问；职位名称为空；AI 生成的内容含编造信息；Workspace 不是并列布局。

### J6 补全必填项、用 Analyze 和 AI 修复，直到可以发布（P0）

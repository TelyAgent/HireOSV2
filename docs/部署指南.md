# HireOS 部署指南

本文档是 HireOS（5 个子系统：Interview / Screening / JD / Written / Core Record）从本地开发到线上服务器的完整部署说明。更细节的踩坑记录见根目录 `PORTS.md` 的"Docker 部署"和"远程部署"两节，本文档是面向"我该怎么操作"的精简版。

## 1. 整体架构

```
浏览器
  │
  ▼
服务器已有 nginx（listen 80，server_name _ 兜底 server block）
  │  location /hireos/ 转发（不碰其他站点配置）
  ▼
HireOS 自己的网关容器 gateway（内部端口 80，宿主机映射到 8830）
  │  按 /interview/ /screening/ /jd/ /written/ /core-record/ 路径前缀转发
  ▼
5 个后端容器 + 4 个前端容器 + 1 个 postgres 容器（docker compose 内部网络，互相用服务名访问）
```

- 本地开发（`scripts/dev.sh`）：5 个后端 + 4 个前端各自跑在固定端口上，外面套一层本地统一网关（`gateway/frontend-gateway.mjs` :8080 / `gateway/backend-gateway.mjs` :8090），跟 Docker 化完全是两条独立的路径，互不影响。
- 本地 Docker 验证（`docker-compose.yml` + `docker-compose.override.yml`）：跟真实部署用同一套镜像定义，只是网关端口本地是裸的 `:80`。
- 远程部署（`docker-compose.yml` + `docker-compose.prod.yml` + `scripts/deploy/deploy.sh`）：网关端口是 `8830`（GCP 防火墙没开放，实际靠服务器自己的 nginx 转发 `/hireos/` 前缀对外访问），前端 build 时多套一层 `/hireos/` 路径前缀。

**线上访问地址**：`http://34.94.189.76/hireos/`（`/interview/`、`/screening/`、`/jd/`、`/written/`、`/core-record/api/v1/...` 都在这个前缀下面）。

## 4. 部署到服务器

跳板机/服务器连接信息已经作为默认值写死在 `scripts/deploy/deploy.sh` 里了（就是第 2 节那张表），**不需要再手动 export 任何环境变量**，直接跑命令就行。以后万一真的换了服务器，可以用同名环境变量覆盖默认值（比如 `REMOTE_ASSET_HOST=新IP scripts/deploy/deploy.sh deploy`）。

### 4.1 首次部署到一台新服务器才需要做

```bash
scripts/deploy/deploy.sh bootstrap   # 装 docker-compose-plugin，建 /opt/hireos 目录结构
scripts/deploy/deploy.sh push-env    # 上传各服务的 .env.production 系列密钥到 shared/env/，不走 git
```

### 4.2 一键部署（改完代码后）

```bash
scripts/deploy/deploy.sh deploy                 # 全部部署（5 后端 + 4 前端 + 网关）
scripts/deploy/deploy.sh deploy jd               # 只部署 JD 子系统（jd-backend + jd-frontend）
scripts/deploy/deploy.sh deploy jd-frontend      # 只部署这一个具体服务
scripts/deploy/deploy.sh deploy backends         # 只部署全部后端（含 core-record）
scripts/deploy/deploy.sh deploy frontends        # 只部署全部前端
```

不管部署全部还是只部署某一个，流程都是：打包本地全部代码（`git ls-files`，自动跳过 `node_modules`/`.env`/`dist` 等，这一步固定是全量的，很快）→ 通过跳板机传到服务器一个新的 `releases/<时间戳>/` 目录 → 软链密钥文件进去 → 远程只对**你指定的目标**跑 `docker compose build && up -d`（没指定就是全部）→ **自动重启一次网关**（除非网关本身就是这次的部署目标，见第 6 节第 1 条）。

只指定一个子系统/服务的好处是：明明只改了一行前端代码，不用再干等全部 10 个镜像重新构建。

子系统分组（`interview`/`screening`/`jd`/`written`）、角色分组（`backends`/`frontends`）、或者直接写 `docker-compose.yml` 里的具体服务名都可以。`postgres` 故意没做成可部署目标——它是用官方镜像的基础设施，不是这个仓库自己 build 的，重启它会让所有后端瞬间断连；真要动它得手动上服务器操作。

### 4.3 其他常用命令

```bash
scripts/deploy/deploy.sh check              # 只读诊断：连接是否正常、docker/compose 版本、有没有已存在的 hireos 项目
scripts/deploy/deploy.sh status             # 查看当前 release 的容器状态
scripts/deploy/deploy.sh logs <service>     # 查看某个服务日志，服务名对应 docker-compose.yml 里的 key
scripts/deploy/deploy.sh push-env           # 改了某个后端的密钥/环境变量后单独重推，不用整套重新部署
```

如果哪次部署完想手动单独重启一下网关（正常不需要，`deploy` 已经自动做了）：

```bash
SSHPASS="$(cat scripts/deploy/.deploy-hireos-remote.password)" \
sshpass -e ssh -o StrictHostKeyChecking=yes -p 2222 -l 'jsunsu@ubuntu@34.94.189.76' 34.92.110.140 \
'sudo docker compose -f /opt/hireos/current/docker-compose.yml -f /opt/hireos/current/docker-compose.prod.yml -p hireos restart gateway'
```

## 6. 已知坑（部署时容易踩，都已经修好，了解原理避免以后重犯）

1. **网关 DNS 缓存**：只重建部分服务时，`gateway` 容器如果本身没被重建，会继续用旧的、已经失效的容器 IP 转发，导致请求打到错误的容器上。已经在 `gateway/nginx.conf` 里加了 `resolver 127.0.0.11 valid=10s;` + 变量形式 `proxy_pass` 做动态解析兜底，`scripts/deploy/deploy.sh deploy` 现在也会在每次部署后自动重启一次网关（除非网关本身就是这次的部署目标），不需要再手动做这一步。
2. **前端 mock 数据陷阱**：`hireos-screening-front` 有个 `VITE_API_MODE` 开关，不等于 `"real"` 就静默走内置假数据，而 `.dockerignore` 排除了 `.env`，导致 Docker 构建时这个变量永远是 `undefined`。已经在 Dockerfile 里给它加了 `ARG VITE_API_MODE=real` 默认值修复。以后新前端如果也做类似的 mock/real 开关，记得同样要在 Dockerfile 里显式给默认值，不能指望 `.env` 文件进 Docker 构建上下文。
3. **Vite `base` 是编译时烤进产物的绝对路径**：不是运行时相对路径，改了外层 nginx 转发前缀（比如这次加的 `/hireos/`）必须同步重新构建前端、把 `base` 也带上新前缀，光改 nginx 转发规则没用。
4. **`docker compose` 对 `ports:` 等列表字段是多文件拼接，不是替换**：本地端口配置放在 `docker-compose.override.yml`（不带 `-f` 时自动加载），远程配置放在 `docker-compose.prod.yml`（远程部署显式 `-f` 加载），两者不会同时生效，靠这个隔离避免端口冲突。
5. **内嵌 git 仓库（历史问题，现在已经不存在了）**：几个子系统目录曾经各自带着独立 `.git`（各自单独 push 到 GitHub 的老习惯），直接 `git ls-files` 打包会漏掉它们的内容或者反而把整个目录（含 `node_modules`）带上，一度把上传体积从几 MB 打包成 2.86GB。后来把这几个目录的改动 commit + push 到各自 GitHub 仓库保底后，删掉了它们的 `.git`，并用 `git rm --cached` + `git add` 让根仓库重新正常追踪这些目录的内容——**删完 `.git` 别忘了这一步**，只删物理目录不会让根仓库的 index 自动更新，会导致根仓库一直把这个路径当成不透明的"内嵌仓库"占位符，`git status`/`git ls-files` 完全看不到内部文件变化，表现就是"看起来什么都没改"但部署上去的其实是旧内容。`scripts/deploy/deploy.sh` 的 `collect_upload_list()` 里还留着当时处理内嵌仓库的兼容代码，现在已经没有目标可处理，是无害的防御性代码。

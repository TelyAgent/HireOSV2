HireOS 演进式组合架构

目标 1：各子系统独立迭代、独立上线　·　目标 2：未来合并时改动尽量少、数据与账号打通。

本文用五张图讲完整件事：图 1、2 讲「最终长什么样 vs 起步怎么建」，图 3 讲「两个目标靠哪一层实现」，图 4 讲「单个子系统长什么样」，图 5 讲「什么时候上线、什么时候合并」。

图 1　目标架构：最终形态（验收视角）

这是最终交付给用户看到的样子：一个系统、一套账号、一份数据。它是验收标准，不是施工图。

图 2　实施架构：起步就按这个建（建设视角）

物理上从第一天就是 N 个独立部署单元。白框 = 一个可独立发布的进程或前端产物。虚线框 = 后续阶段接入。

子系统访问数据只有三条路径。图里 ① 和 ② 是两条互不相干的线 —— 落库从来不经过事件总线。

① 读写自己的私有表：直连自己的 schema，本地事务，不经任何中间件；② 读写主档：调 Core Record 同步 API，拿不到主档库连接；③ 告诉别人我变了：往事件总线发一条事件，这是子系统之间唯一的通道。

Core Record Service 是干什么的

它是「同一个人、同一个岗位、同一次投递」在全部子系统里的唯一一份档案，也是唯一能写这份档案的进程。它管四样东西：Candidate（这个人）、Job（这个岗位）、Application（这个人对这个岗位的这次投递）、File（文件）。

为什么必须单独拎出来：如果 JD 自己存一份岗位、Screening 自己再存一份，合并时就会出现「同一个岗位有两个版本、不知道该信谁」。集中成一份之后，五个子系统引用的是同一个 job_id、同一个 application_id，这才是「数据能打通」的物理基础。JD 创建岗位是调它的 API 让它写，不是自己写一份。

为什么图里没有「集成域」

这个词已废弃。它原本装在三样东西，但没有一样构成一个层或一个域：事件总线就是一个消息中间件（和 Kafka 同类，S0 用已有的 Redis Streams，不新建），已并入 L0 基础设施；Schema Registry 是事件格式的文件仓库 + 一条 CI 校验，不是运行时；子系统注册表 是 Shell 的配置，跟着 Shell 走。剩下的只有规则，不是东西 —— 三条：跨系统只能发事件、主档只能经 Core Record、A 不许直接调 B。

事件总线和 Queue 是不是重复

技术上不重复的两个产品，是同一个 Redis 上的两种用法：Queue 是一条活只干一次、消费完删除（AI 解析、发邮件、导入）；事件总线是一件事广播给多方、保留可重放（岗位发布 → Screening 建投影、Tasks 生成任务、Timeline 记一笔）。等事件需要长期留存、需要重放补数、订阅方和量级上来了，再把事件总线换成 Kafka —— 因为消费者只认标准 envelope，换的时候不改业务代码。

为什么不能照着图 1 直接建

把图 1 当成施工图，就会建成一个单体，两个目标同时失守。

做法照图 1 直接建（单体）照图 2 建（本文方案）
代码与库一个进程、一个库，五个业务域共用表每个子系统独立进程、独立 schema，主档由 Core Record 独占写入
改一个业务域要全量回归、整体发版，其他域陪跑只发自己的进程，其他域不动
目标 1 独立上线做不到天然满足
目标 2 后期合并表面已经"合"了，但合并的是代码耦合，不是能力组合合并发生在组合层与注册表，子系统不改
代价前期快，后期每加一个域都更慢S0 阶段无业务产出，之后每个新域成本恒定

一句话：图 1 是"合完之后看起来什么样"，图 2 是"怎么建才能合得起来"。直接照图 1 建，等于把目标当成了施工图。

图 3　两个目标分别靠哪几层实现

左右是同一套四层，只是高亮不同：左图 = 目标 1 生效在哪几层，右图 = 目标 2 生效在哪几层。灰色 = 该层对此目标不起决定作用。

原本设过一层「契约与集成层」，现已撤销：事件总线归入 L0 基础设施，子系统注册表归入 L3 组合层，API 与事件契约改为跨层纪律（见底部紫条）。分层从五层减为四层，没有信息丢失。

图 4　单个子系统视角：它对外的全部接口

以 Screening 为例。它自己只有四样东西，其余全靠左边地基、右边事件总线与注册表——所以换掉它或新增别的系统，都不影响别人。

图 5　时序：什么时候上、什么时候合并、合并时改什么

深色是「本阶段新增」，浅色是「已上线、持续运行、不改动」。合并不是一次性开关，随子系统接入逐级发生。

一句话总结

不是「先拆开，以后再想办法合」，而是「第一天就按合完之后的样子建好插座，子系统一个个插上来」。

图 1 是插座通电后的样子，图 2 是插座本身，图 5 是通电顺序。

# HireOS 演进式组合架构

目标 1：各子系统独立迭代、独立上线 · 目标 2：未来合并时改动尽量少、数据与账号打通。

本文用五张图讲完整件事：**图 1、2** 讲「最终长什么样 vs 起步怎么建」，**图 3** 讲「两个目标靠哪一层实现」，**图 4** 讲「单个子系统长什么样」，**图 5** 讲「什么时候上线、什么时候合并」。

> **子系统访问数据只有三条路径。图里 ① 和 ② 是两条互不相干的线 —— 落库从来不经过事件总线。**
> ① **读写自己的私有表**：直连自己的 schema，本地事务，不经任何中间件；② **读写主档**：调 Core Record 同步 API，拿不到主档库连接；③ **告诉别人我变了**：往事件总线发一条事件，这是子系统之间唯一的通道。

**Core Record Service 是干什么的**

它是「**同一个人、同一个岗位、同一次投递**」在全部子系统里的**唯一一份档案**，也是唯一能写这份档案的进程。它管四样东西：Candidate（这个人）、Job（这个岗位）、Application（这个人对这个岗位的这次投递）、File（文件）。

为什么必须单独拎出来：如果 JD 自己存一份岗位、Screening 自己再存一份，合并时就会出现「同一个岗位有两个版本、不知道该信谁」。集中成一份之后，五个子系统引用的是同一个 `job_id`、同一个 `application_id`，这才是「数据能打通」的物理基础。JD 创建岗位是**调它的 API 让它写**，不是自己写一份。

**为什么图里没有「集成域」**

这个词已废弃。它原本装在三样东西，但没有一样构成一个层或一个域：**事件总线**就是一个消息中间件（和 Kafka 同类，S0 用已有的 Redis Streams，不新建），已并入 L0 基础设施；**Schema Registry** 是事件格式的文件仓库 + 一条 CI 校验，不是运行时；**子系统注册表** 是 Shell 的配置，跟着 Shell 走。剩下的只有规则，不是东西 —— 三条：跨系统只能发事件、主档只能经 Core Record、A 不许直接调 B。

**事件总线和 Queue 是不是重复**

技术上不重复的两个产品，是**同一个 Redis 上的两种用法**：Queue 是一条活只干一次、消费完删除（AI 解析、发邮件、导入）；事件总线是一件事广播给多方、保留可重放（岗位发布 → Screening 建投影、Tasks 生成任务、Timeline 记一笔）。等事件需要长期留存、需要重放补数、订阅方和量级上来了，再把事件总线换成 Kafka —— 因为消费者只认标准 envelope，换的时候不改业务代码。

## 为什么不能照着图 1 直接建

把图 1 当成施工图，就会建成一个单体，两个目标同时失守。

| 做法 | 照图 1 直接建（单体） | 照图 2 建（本文方案） |
| --- | --- | --- |
| 代码与库 | 一个进程、一个库，五个业务域共用表 | 每个子系统独立进程、独立 schema，主档由 Core Record 独占写入 |
| 改一个业务域 | 要全量回归、整体发版，其他域陪跑 | 只发自己的进程，其他域不动 |
| 目标 1 独立上线 | **做不到** | 天然满足 |
| 目标 2 后期合并 | 表面已经"合"了，但合并的是代码耦合，不是能力组合 | 合并发生在组合层与注册表，子系统不改 |
| 代价 | 前期快，后期每加一个域都更慢 | S0 阶段无业务产出，之后每个新域成本恒定 |

> **一句话：图 1 是"合完之后看起来什么样"，图 2 是"怎么建才能合得起来"。直接照图 1 建，等于把目标当成了施工图。**

## 图 3 两个目标分别靠哪几层实现

左右是**同一套四层**，只是高亮不同：左图 = 目标 1 生效在哪几层，右图 = 目标 2 生效在哪几层。灰色 = 该层对此目标不起决定作用。

原本设过一层「契约与集成层」，现已撤销：事件总线归入 L0 基础设施，子系统注册表归入 L3 组合层，API 与事件契约改为跨层纪律（见底部紫条）。分层从五层减为四层，没有信息丢失。

```text
┌──────────────────────────────────────────┐   ┌────────────────────────────────────────┐  
│目标 1 · 独立迭代、独立上线               │   │目标 2 · 合并时改动尽量少               │  
│任一子系统发布，不需要其他子系统配合或停机│   │新增子系统时，已上线的业务代码改动为 0  │  
└──────────────────────────────────────────┘   └────────────────────────────────────────┘  
┌────────────────────────────────────────┐     ┌────────────────────────────────────────┐  
│L3 体验组合层  不参与                   │     │L3 体验组合层  核心                     │  
│子系统不依赖组合层也能独立运行          │     │注册表驱动，加一个子系统 = 加一条配置   │  
└────────────────────────────────────────┘     └────────────────────────────────────────┘  
┌────────────────────────────────────────┐     ┌────────────────────────────────────────┐  
│L2 业务子系统层  核心                   │     │L2 业务子系统层  不改                   │  
│独立进程 · 独立 schema · 独立前端 bundle│     │接入后不再改动，横向零直调              │  
└────────────────────────────────────────┘     └────────────────────────────────────────┘  
┌────────────────────────────────────────┐     ┌──────────────────────────────────────────┐
│L1 平台地基层  保障                     │     │L1 平台地基层  核心                       │
│地基独立部署，子系统各自依赖而非互相依赖│     │账号 / 主档 / 审计第一天统一，后期不换主键│
└────────────────────────────────────────┘     └──────────────────────────────────────────┘
┌────────────────────────────────────────┐     ┌────────────────────────────────────────┐  
│L0 基础设施（含事件总线）  底座         │     │L0 基础设施（含事件总线）  底座         │  
│共用，靠 schema 与命名空间隔离          │     │事件总线是合并时要对接的接缝，但本身不改│  
└────────────────────────────────────────┘     └────────────────────────────────────────┘  
```

> **横向纪律 · 契约与注册表只加不改（不属于任何一层）**：API 与事件 schema 集中登记、CI 做破坏性变更检测 —— 它同时服务两个目标，但不占一个层，也不多一个部署单元。

> 同一套四层，两个目标生效的层不同：L1 同时服务两个目标 —— 它是 S0 必须一次建好的部分，也就是「提前付的一次性成本」。

## 图 4 单个子系统视角：它对外的全部接口

以 Screening 为例。它自己只有四样东西，其余全靠左边地基、右边事件总线与注册表——所以换掉它或新增别的系统，都不影响别人。

```text
┌──────────────────────┐  ┌─────────────────────────────────────────────┐  ┌─────────────────────────────────────────────────┐
│L1 平台地基           │  │业务子系统 · 以 Screening 为例               │  │L3 组合层 / 注册表 / 事件总线                    │
│Identity              │  │前端 bundle                                  │  │L3 Shell（含注册表）                             │
│  账号 · 组织 · 权限  │  │  可无导航嵌入 · 稳定深链                    │  │  登录 · 导航装配 · 统一 Tasks 聚合，只消费注册表│
│Core Record           │  │API 服务                                     │  │注册表                                           │
│  主档唯一写入方      │  │领域逻辑与业务动作                           │  │  identity · ui · api · events                   │
│Audit / Timeline      │  │私有库 schema                                │  │  上线时登记一次，组合层自动装配                 │
│  决策 · 时间线 · 审计│  │  只存自己的表，主档只存引用 ID              │  │事件总线 + Schema Registry                       │
└──────────────────────┘  │对外契约                                     │  │  子系统之间唯一允许的通道                       │
                          │  OpenAPI · produced/consumed 事件 · 注册条目│  │  禁止 A 直接调用 B                              │
                          └─────────────────────────────────────────────┘  │  事件只带 ID 与变更摘要                         │
                                                                           └─────────────────────────────────────────────────┘
```

> 基础设施：Postgres + pgvector · Redis · Queue · 事件总线 · 对象存储 · 可观测性 —— 全部部署单元共用

## 图 5 时序：什么时候上、什么时候合并、合并时改什么

深色是「本阶段新增」，浅色是「已上线、持续运行、不改动」。合并不是一次性开关，随子系统接入逐级发生。平台地基各阶段常驻（持续运行，不改动）。

| 阶段 | 本阶段新增 | Shell | 已上线子系统（业务代码改动） | 合并状态 |
| --- | --- | --- | --- | --- |
| S0 地基就绪 | 平台地基 + 空 Shell | 空壳 | —（无已上线） | 未开始 |
| S1 首个上线 | JD | 1 个入口 | —（无已上线） | 单系统运行 |
| S2 第二个 | Screening | 跨系统视图 | JD：0 行 | ① 一二合并（I2 事件打通） |
| S3 三·四接入 | Assessment · Interview | 统一 Tasks | JD · Screening：0 行 | ② 一~四合并（I3 编排打通） |
| S4 全量组合 | Offer + 统一指标 | 统一编排与指标 | 前四个：0 行 | ③ 全量合并（I4 统一体验） |

## 一句话总结

> **不是「先拆开，以后再想办法合」，而是「第一天就按合完之后的样子建好插座，子系统一个个插上来」。**
> 图 1 是插座通电后的样子，图 2 是插座本身，图 5 是通电顺序。

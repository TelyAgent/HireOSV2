| 属性 | 定义 |

| 版本 / 日期 | v1.1 / 2026-09-08（沿用原文件路径） |
| 设计依据 | [独立子系统与邮件驱动架构 v2.0](HiOS_Command_Module_Boundaries_and_Interface_Spec_v2.0.md) |

## 1. 推荐邮箱规划

采用“三类邮箱”：公司招聘入口、子系统共享邮箱、员工个人邮箱。候选人使用其确认的外部联系邮箱。

### 1.1 默认公司邮箱

| 邮箱 | 角色 | 主要接收 | 主要发出 | 默认管理人 |
|---|---|---|---|---|
| **hr@sendinglabs.com** | 候选人统一对外收发身份 | CV、求职咨询、全流程候选人回复 | 招聘答复、测评邀请、面试通知、正式 Offer 与后续沟通 | 招聘运营负责人 / HR 团队 |
| **jd@sendinglabs.com** | JD 子系统共享邮箱 | 岗位需求、旧 JD、修改意见 | 草稿审阅、岗位定义结果和修订通知 | JD 运营负责人 |
| **screening@sendinglabs.com** | 简历筛选子系统共享邮箱 | 从 HR 或其他来源转入的简历、岗位资料 | 筛选待办、报告、补充资料请求 | 筛选运营负责人 |
| **assessment@sendinglabs.com** | 测评子系统内部共享邮箱 | 测评请求、名单、材料、路由后的回复 | 内部评分任务与结果；候选人邮件统一由 hr@ 发出 | 测评运营负责人 |
| **interview@sendinglabs.com** | 面试子系统内部共享邮箱 | 面试请求、简历/JD、补充证据、路由后的回复 | 内部计划、面试官提醒、反馈任务与评估；候选人邮件统一由 hr@ 发出 | 面试协调负责人 |
| **offer@sendinglabs.com** | Offer 子系统内部共享邮箱 | 录用请求、评估依据、条款资料、路由后的回复 | 内部审批任务；候选人 Offer 与回应确认统一由 hr@ 发出 | Offer 运营负责人 |
| **hios-admin@sendinglabs.com** | 全局账号与配置运营邮箱 | 连接异常、权限请求、无法路由的系统异常 | 账号邀请、配置通知、运营异常通知 | 系统管理员 |

共建议七个功能地址：一个招聘入口、五个业务子系统地址、一个管理地址。`hr@` 为用户已指定的入口，其余地址为建议，需由企业管理员配置。

`hr@` 属于公司通用入口，不归 Screening 独占。候选人将 CV 发到 `hr@` 后，可以根据岗位规则或 HR 的选择进入筛选、测评、面试或其他处理路径，不要求先经过 Screening。

### 1.1.1 对外统一身份，内部按模块路由

候选人从投递 CV 到测评、面试和 Offer，默认始终看到 **Sendinglabs 招聘团队 <hr@sendinglabs.com>**。各业务系统负责生成自己的通知、校验业务条件和保存本地记录，通过 M0 授权的邮件连接使用统一对外身份发送。内部模块邮箱不作为候选人的默认沟通入口，也不放入候选人邮件的默认 Cc 或签名。

| 受众 | From / Reply-To | 业务处理方 |
|---|---|---|
| 候选人：测评 | hr@sendinglabs.com | Assessment |
| 候选人：面试 | hr@sendinglabs.com | Interview |
| 候选人：Offer | hr@sendinglabs.com | Offer |
| 员工：面试任务 | interview@sendinglabs.com | Interview |
| 模块交接：面试结果到 Offer | interview@sendinglabs.com → offer@sendinglabs.com | 各自本地处理 |

M0 邮件接入层只管理发送身份、收发连接和消息路由，不拥有招聘案件或决定。发送时记录所属子系统、本地案件/任务、实际邮件标识和发送状态；回复时按映射转入相应限定队列。子系统无需读取整个 hr@ 邮箱，也不依赖另一个业务子系统。目标系统暂时离线时，回复保留待投递，恢复后去重处理。

日历邀请、改期和取消邮件也应采用一致的候选人可见招聘身份；会议及日历集成需确认实际发送者/组织者行为，不默认假定日历会继承普通邮件的 From 配置。内部 Brief 和反馈任务另外发给员工。

### 1.2 功能地址不等于必须购买七个独立账号

推荐各子系统有独立共享邮箱，以便分别授权、运营、审计和处理回复。若企业邮件平台采用别名，也可使用独立地址配合受控文件夹/队列和路由，但需要确保模块连接只能读取被授权范围；只分地址、实际所有模块都能读取整个 HR 邮箱，不满足隔离目标。

共享邮箱是团队资源，不采用多人共享密码登录。员工用个人公司身份访问获授权的共享邮箱；系统用管理员批准的连接身份执行收发。邮箱产品、许可和具体连接方式在选定邮件平台后实施。

### 1.3 员工个人邮箱

| 业务角色 | 地址来源 | 接收任务 |
|---|---|---|
| Case Owner / HR Recruiter | M0 中该员工已验证的公司邮箱 | 建档确认、补资料、排期、异常、结果和交接 |
| Hiring Manager | 岗位/案件上的负责人账号 | 面试计划确认、Debrief、评估复核、录用意向 |
| Interviewer | 本次面试官账号 | 面试邀请、Brief、提醒、本人反馈任务 |
| Backup Owner | 案件上的备用负责人账号 | 无负责人、逾期、退信等升级任务 |
| Candidate | 案件中确认的外部邮箱 | 排期、确认、参与提醒、本人需补充资料 |

个人邮箱从账号和案件角色分配读取，不猜测姓名拼写，不用全公司员工列表群发。一个人兼任多个角色时合并适用通知，保留清晰任务；多位面试官的反馈任务分别投递。

### 1.4 候选人个人邮箱与访问边界

候选人个人邮箱是通知体系的正式组成部分，属于外部参与者邮箱，不要求使用 `@sendinglabs.com`。面试通知默认以 **Sendinglabs 招聘团队 <hr@sendinglabs.com>** 发往案件中已确认的候选人个人邮箱，Reply-To 同样为 `hr@sendinglabs.com`。

| 场景 | 向候选人发送的内容 | URL / 回复方式 |
|---|---|---|
| 补充资料 | 明确需要候选人提供的资料 | 本人上传页面；可回复附件 |
| 排期邀请 | 可选时间、时区与确认要求 | 受限选时/确认页面 |
| 面试确认 | 日期、时间、时区和参与方式 | 本人面试安排与参与入口 |
| 面试前提醒 | 当前有效安排与准备说明 | 面试参与入口 |
| 改期或取消 | 最新安排、变更和需确认事项 | 当前安排页面 |
| 后续面试 | 新轮次及下一步要求 | 新轮次排期/参与入口 |

候选人无需开通公司员工账号，通过 M0 支持的受限邀请身份或验证流程进入自己的页面，仅可查看本人安排、提交资料和参与面试。不能访问内部 Interview Brief、面试官 Scorecard、Debrief 或未获准披露的 Hiring Evaluation。

候选人回复进入 `hr@`，由 M0 管理的邮件接入层按原发出邮件关联信息，将对应回复路由到 Interview 的限定队列并归入本地案件；需要人工处理时创建本地任务，再通知案件 HR 的公司个人邮箱。无法确定案件的回复进入待分类队列。候选人邮件与内部任务邮件分别生成，不通过共同抄送链交付。

候选人联系邮箱需在发送邀请前确认；候选人申请修改地址时，核验身份后更新本地联系方式和受影响邀请，保留变更记录。转发邮件或持有旧 URL 不自动赋予他人访问权。

本小节定义候选人邮箱的角色和访问范围；第 5 节统一维护完整发送矩阵，第 8 节统一维护链接与操作权限规则。

## 2. 收件、存储和任务分配是三个不同动作

**收进共享邮箱，是收到输入；保存到面试子系统，是建立可用业务资料；发到个人邮箱，是把任务交给责任人。**

| 内容 | 权威位置 | 邮箱中的作用 |
|---|---|---|
| 原始来信与附件 | 公司邮箱保留原件；Interview 保存获授权导入的必要副本及来源信息 | 输入渠道与沟通历史 |
| 候选人、岗位、面试目标 | Interview 本地案件数据库中的版本化快照 | 邮件可提交或补充，但不充当唯一主档 |
| 简历、JD、报告、问答附件 | Interview 本地受控文件/对象存储，或其独立管理的公司文件位置 | 附件或文件链接作为传输入口 |
| 面试计划、场次、任务、Scorecard、决定 | Interview 本地数据库 | 通知提供当前任务 URL |
| AI 生成与人工修订 | Interview 本地版本和追溯记录 | 只发送适用摘要，不以旧邮件覆盖新结果 |
| 收发与失败状态 | Interview Inbox/Outbox 及邮件连接反馈 | 记录来信、发送、退信、重试和关联 |

**面试系统不能每次打开案件时再从 HR 邮箱临时拼出资料。** 合法导入完成后，即使原邮件被移动、来源系统停机或其他业务模块未启用，本地案件仍可运行。访问撤回与删除请求仍需按策略对已导入副本处理。

## 3. Interview 从哪里读取数据

### 3.1 默认路径：HR 统一收 CV，选择后转入 Interview

```text
候选人邮箱
   → hr@sendinglabs.com：CV / 求职邮件
   → HR 选择岗位和处理路径
   → interview@sendinglabs.com：面试请求 + CV + JD/目标
   → Interview 本地 Intake
   → HR 个人邮箱：请确认面试案件（URL）
```

HR 可以在共享邮箱中转发，也可以从已授权的 HR 收件队列点击“发起面试”，由公司邮件连接向 `interview@` 发送交接包。前者保留原始来源，后者按已配置的发送身份发送；都不需要 Screening 运行。

建议发起面试请求包含：候选人、岗位/面试目标、HR 负责人、Hiring Manager、简历/背景资料和 JD；面试官、建议时间、筛选或笔试报告可以后补。系统可以先建 Intake，具体面试启动前再确认必要字段。

**不是每封到达 `hr@` 的 CV 都自动创建面试。** 默认由 HR 选择或由其预先批准的岗位路由规则决定；缺岗位或动作不明确时留在 HR 待分类队列。

### 3.2 可用的其他输入路径

| 路径 | Interview 如何读取 | 不要求什么 |
|---|---|---|
| HR/Hiring Manager 直接发给 interview@ | 读取该模块邮箱中新邮件和附件，建立 Intake | 不要求先收到 hr@ |
| screening@ / assessment@ 发结果 | 导入所附报告及业务快照 | 不实时查询来源模块 |
| 公司共享文件位置 | 读取获授权的指定文件/目录，验证完成状态，导入副本 | 不读取整个公司盘 |
| 员工打开 Interview URL 上传 | 按登录用户权限上传并关联案件 | 不要求先发邮件；导入仍触发通知 |
| 候选人回复面试邮件到 hr@ | 邮件接入层按原发出邮件关联路由，Interview 仅接收本案件的沟通/待确认资料 | 不因回复邮件而获得内部评估权限 |

Interview 默认只订阅 `interview@` 的授权收件范围，不直接扫描 HR、Hiring Manager 或面试官个人邮箱。需要从 `hr@` 自动读取时，应由 M0 为通用 HR Intake 配置限定规则或明确授予指定队列权限，不能默认为整个邮箱可访问。

### 3.3 收件后的处理

1. 邮件连接收到新消息通知，或按已配置方式增量读取授权邮箱。
2. 保存接收记录：来源邮箱、发件人、收件人、原始消息标识、时间、主题、关联及附件清单。
3. 验证路由、资料类型和重复情况；来信自报身份不能替代员工权限。
4. 解析候选人、岗位、请求动作和附件；对无法确定的信息标记待确认。
5. 创建或关联本地 `InterviewCase`，导入必要资料，分配本地负责人。
6. 从 `interview@` 向负责人个人公司邮箱发“已收到，请确认”通知，URL 直达该 Intake。
7. 员工登录后确认候选人联系方式、岗位、负责人和资料；确认后进入正式计划流程。

没有可靠负责人时，分配给 Interview 运营队列并通知配置好的备用负责人；不自动认定任意发件人是 HR 或 Hiring Manager。

## 4. Interview 数据如何存放

### 4.1 本地对象

| 本地对象 | 关键内容 |
|---|---|
| InterviewCase | 本地案件 ID、组织、候选人/岗位关联、负责人、状态、版本 |
| CandidateSnapshot | 本地候选人标识、姓名、已确认联系邮箱、背景资料版本 |
| RoleSnapshot | 岗位名称、要求、面试目标、评分标准及来源版本 |
| InputArtifact / Evidence | 文件 ID、来源邮件/文件、摘要、哈希、访问范围、用途和验证状态 |
| InterviewPlan / Session | 轮次、面试官、时间、时区、会议方式、目标与邀请状态 |
| Task / Scorecard / Debrief | 责任人、截止时间、本人反馈、复核与决定 |
| Communication / Notification | 来信关联、通知模板、收件人、任务、发送和回执状态 |
| HiringEvaluationPackage | 结果版本、证据、缺口、人工结论、已交付接收方 |

无须共享 Candidate/Application 服务。跨模块 ID 仅作为可选来源映射；本地案件独立生成 ID。

### 4.2 文件组织示意

以下是逻辑结构，不是已创建的目录，也不要求固定采用文件目录数据库：

```text
interview / {workspace} / {case_id} /
  inputs /      原始导入的简历、JD、筛选/测评报告
  sessions /    各场次的获准记录与附件
  evidence /    新增证据、来源定位与版本
  outputs /     评估报告、summary.md、结构化交接包
```

使用不可推断的 ID，避免以姓名和邮箱直接作为对外文件路径。数据库保存文件引用和权限，文件存储保存内容；历史文件不被新版本静默覆盖。普通员工的任务邮件默认不附内部完整资料包，而是进入受控页面读取。

### 4.3 去重与邮件关联

系统交接使用 `exchange_id + version`；普通邮件使用原始消息标识、附件校验及已确认案件关联检测疑似重复。回复通过 In-Reply-To/References、稳定关联信息或经支持的案件回复路由关联，不能只按主题或候选人姓名归档。

候选人邮件的 From 与 Reply-To 统一为 `hr@sendinglabs.com`，不默认使用暴露模块名的回复别名。内部面试任务邮件的 From 与 Reply-To 使用 `interview@sendinglabs.com`。邮件接入层保存实际发出消息的标识与目标模块、本地案件之间的映射；回复缺少关联头、跨案件混杂或存在歧义时，进入 HR 待分类队列，不仅按邮箱、姓名或最近阶段自动分配。

## 5. 面试流程中的邮件发送矩阵

发送矩阵按收件角色选择身份：**候选人邮件 From/Reply-To 均为 hr@sendinglabs.com，显示名称为 Sendinglabs 招聘团队；员工面试任务与模块交接邮件 From/Reply-To 为 interview@sendinglabs.com。** 同一事件同时涉及内外参与者时分别发信。系统以批准的公司发送身份发送，员工个人邮箱是任务接收方，不是系统默认冒用的发件人。

| 阶段/事件 | 输入或本地动作 | To | Cc / 其他路由 | 正文和 URL |
|---|---|---|---|---|
| HR 收到 CV | 候选人 → hr@ | HR 个人邮箱（仅在需要处理时） | hr@ 中保留原信 | HR 收件处理任务；此通知可由通用 Intake 发出 |
| 面试请求已导入 | HR/系统 → interview@ | 案件 HR 个人邮箱 | 不默认群抄送 | 已收资料、待确认字段、Intake URL |
| 缺资料 | 本地识别不足 | 能补齐该资料的人 | 必要时单独通知 HR | 具体缺失项、补充 URL；允许回复附件 |
| 计划待确认 | AI/HR 准备计划 | Hiring Manager 个人邮箱 | HR 按配置订阅 | 面试目标/轮次摘要、确认计划 URL |
| 面试官待确认 | HR 指定面试官 | 各面试官个人邮箱 | HR 收汇总状态 | 本人职责与时间、确认 URL |
| 候选人排期邀请 | 本地计划已确认 | 候选人已确认邮箱 | 默认不抄送内部评审邮件 | 选时/确认 URL、时区、必要说明 |
| 面试时间已确定 | 参与者完成确认 | 候选人；各面试官分别发送 | HR 收内部汇总 | 候选人参与入口；面试官 Brief/场次入口；可附日历文件 |
| 面试前提醒 | 到达设定提醒时间 | 候选人；各面试官分别发送 | 无默认 Cc | 当前时间、参与或执行 URL |
| 面试完成待反馈 | 场次完成 | 该场次各面试官个人邮箱 | HR 查看完成率，不收他人待填表 | 本人 Scorecard URL、期限 |
| 反馈逾期 | 本地任务未完成 | 逾期面试官个人邮箱 | 达到升级阈值后单独发 HR/HM | 未完成任务和期限，不重复给已完成人发送 |
| Debrief 待复核 | 必需反馈完成或明确缺口 | Hiring Manager 及指定评审人个人邮箱 | HR 按职责接收 | 证据/分歧摘要、Debrief URL |
| 需要补面 | HM 提交补证要求 | 案件 HR；指定面试官各自接收任务 | 候选人另发新的排期邮件 | 具体缺口、各角色任务 URL |
| 评估报告完成 | 人工复核后发布 | HR、Hiring Manager 个人邮箱 | 可按规则向 hr@ 归档发送；不是默认抄送所有人 | Hiring Evaluation 摘要、报告 URL |
| 向 Offer 交接 | HR 明确转交或预授权规则触发 | offer@sendinglabs.com | HR 个人邮箱另收交付通知 | 自包含评估包、请求动作、来源信息 |
| 不使用 Offer 系统 | HR 选择人工/外部处理 | 指定 HR 个人邮箱或获授权外部接收者 | 按需 hr@ 归档 | 可独立阅读报告和文件包 |
| 报告修订/撤回 | 发布新版本/撤回通知 | 登记的结果接收者 | 包括已接收的 offer@（如适用） | 变更、影响和当前版本 URL |
| 收件/发送异常 | 连接、解析或退信异常 | Interview 运营负责人个人邮箱 | 连接问题通知 hios-admin@ | 失败对象、恢复任务 URL |

`hr@` 是资料入口和团队运营资源，**不是每一封内部任务邮件的必需抄送人**。任务直接发到被分配员工的个人公司邮箱，HR 团队通过共享案件权限和运营视图追踪；这可以避免所有过程邮件淹没 HR 收件箱。

## 6. 一次面试的完整示例

以下人员地址仅为示例，不代表真实员工或已配置账号：

- HR Recruiter：`alice@sendinglabs.com`
- Hiring Manager：`bob@sendinglabs.com`
- Interviewer：`carol@sendinglabs.com`
- Candidate：`candidate@example.com`

```text
1. candidate@example.com → hr@sendinglabs.com
   CV 与求职说明。

2. alice@sendinglabs.com → interview@sendinglabs.com
   发起面试，附 CV、JD，指定 Bob 为 HM、Carol 为面试官。

3. interview@sendinglabs.com → alice@sendinglabs.com
   “面试资料已导入，请确认案件” → Intake URL。
   Alice 登录确认，资料保存在 Interview 本地。

4. interview@sendinglabs.com → bob@sendinglabs.com
   “请确认面试计划” → Plan URL。

5. interview@sendinglabs.com → carol@sendinglabs.com
   “请确认面试安排” → 本人安排 URL。
   hr@sendinglabs.com → candidate@example.com
   “请选择/确认面试时间” → 候选人受限排期 URL。

6. interview@sendinglabs.com → carol@sendinglabs.com
   内部确认与提醒，Carol 看 Brief。
   hr@sendinglabs.com → candidate@example.com
   候选人确认与提醒，只看参与信息。
   Candidate 回复 hr@ 后，由邮件接入层关联回本 Interview 案件。

7. interview@sendinglabs.com → carol@sendinglabs.com
   “请提交面试反馈” → Scorecard URL。
   Carol 提交后，反馈保存在 Interview，不要求邮件回复评分。

8. interview@sendinglabs.com → bob@sendinglabs.com
   “招聘评估待复核” → Debrief URL。
   Bob 完成结论，Interview 发布 Hiring Evaluation。

9. interview@sendinglabs.com → Alice / Bob
   “评估已完成” → Report URL。

10. Alice 选择交给 Offer 后：
    interview@sendinglabs.com → offer@sendinglabs.com
    发送必要评估内容和附件包。
    offer@sendinglabs.com → alice@sendinglabs.com
    “录用请求已收到，请确认” → Offer 自己的案件 URL。
```

每个 URL 指向对应子系统真实配置域名下的具体任务，本文不编造可用链接。系统发出的邮件必须记录适用业务规则或操作者；不因邮件中写了某人的地址就直接授予角色和启动对外邀请。

## 7. 收件人如何自动确定

通知引擎使用本地案件的角色映射解析收件人：

```text
事件 InterviewFeedbackRequested
→ 读取 session.interviewer_actor_ids
→ 向 M0 解析这些员工当前有效的公司邮箱和账号权限
→ 每人创建自己的 feedback_task
→ 每人生成单独通知和任务 URL
→ 写入本地 Outbox
→ 通过 interview@ 发送
```

Hiring Manager 通知读取 `case.hiring_manager_actor_id`；HR 通知读取 `case.owner_actor_id`；候选人通知读取已确认的 `candidate.contact_email`；下游交接读取 M0 的已配置目标路由。

人员离职、角色变化、地址失效或任务转派时，停止旧任务提醒，通知新负责人；旧 URL 仍校验当前权限。没有收件人时保留异常任务并通知备用运营人，不发送到猜测的地址。

## 8. 邮件与页面的权限、状态规则

1. 点击邮件 URL 只导航，不自动提交反馈、批准或发放。邮件扫描器打开链接不能完成任务。
2. 员工登录使用 M0 账号；候选人使用受限邀请身份，只看本人安排和获准资料。
3. 面试官只能提交自己的 Scorecard；独立反馈前默认不显示其他面试官评分。
4. 候选人邮件与内部评审邮件分别生成，不把内部报告放在共同 Cc 链中。
5. 回复可补资料或请求改期；任意一句“同意”不默认等于正式审批。此类操作进入页面确认。
6. 已完成任务停止提醒；旧邮件链接打开时展示当前状态。不要为了新通知重复创建案件。
7. 邮件已发送、已送达、资料已导入、任务已完成分别记录；没有打开跟踪不等于用户没处理。
8. 邮箱故障时本地计划、反馈和报告继续保存，待发邮件进入队列；负责人可在页面看到异常并使用文件交付。

## 9. 实施配置清单与验收

| 配置 | 最小要求 |
|---|---|
| 功能邮箱 | hr@、五个模块地址、hios-admin@ 的实际邮箱/别名与所有者 |
| 邮件连接 | 模块限定读取范围；候选人统一 hr@ 发送授权；实际消息标识与模块/案件映射；回复和退信路由 |
| 员工目录 | actor_id、个人公司邮箱、有效账号状态、模块权限 |
| 案件角色 | HR Owner、HM、面试官、备用运营人 |
| 子系统入口 | 实际 Base URL、案件/任务页面、内部认证和候选人邀请机制 |
| 数据存储 | Interview 本地数据库、文件位置、版本和用途访问策略 |
| 通知模板 | 触发事件、收件角色、主 URL、候选人与内部文案、提醒/升级规则 |
| 交接规则 | 是否自动转交、由谁批准、目标邮箱、发送的数据范围 |

验收必须覆盖：只启用 M0+Interview 仍能从邮件 CV/JD 完成面试；任务到达正确员工个人邮箱；候选人不收到内部评分；不读取员工私人收件范围；本地资料在来源停机后可用；转发/重试不重复建档；下游未启用仍能邮件或文件交付；公司邮箱暂时故障不丢失业务结果。
